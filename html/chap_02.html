Chương 2

Where Clause

Chương trước đã mô tả cấu trúc index và giải thích nguyên nhân index performance kém. Bước tiếp theo, chúng ta sẽ học cách nhận diện và tránh các vấn đề này trong SQL statement. Chúng ta bắt đầu bằng where clause.

Where clause định nghĩa điều kiện tìm kiếm của một SQL statement, vì vậy nó thuộc phạm vi chức năng cốt lõi của index: tìm dữ liệu nhanh. Dù where clause có ảnh hưởng rất lớn đến performance, nó thường được viết cẩu thả khiến database phải scan một phần lớn index. Kết quả là where clause viết kém là thành phần đầu tiên của query chậm.

Chương này giải thích các operator khác nhau ảnh hưởng việc sử dụng index thế nào và cách bảo đảm index dùng được cho nhiều query nhất có thể. Phần cuối trình bày các anti-pattern thường gặp và các lựa chọn thay thế có performance tốt hơn.

Equality Operator#

Equality operator vừa là SQL operator đơn giản nhất vừa được dùng thường xuyên nhất. Các lỗi indexing ảnh hưởng performance vẫn rất phổ biến, và where clause kết hợp nhiều điều kiện đặc biệt dễ gặp lỗi.

Phần này chỉ ra cách xác minh việc dùng index và giải thích cách concatenated index có thể tối ưu các điều kiện kết hợp. Để dễ hiểu, chúng ta sẽ phân tích một query chậm để thấy tác động trong thực tế của những nguyên nhân đã giải thích ở Chương 1.

Primary Key#

Chúng ta bắt đầu với where clause đơn giản nhất nhưng phổ biến nhất: primary key lookup. Trong các ví dụ xuyên suốt chương này, chúng ta dùng table EMPLOYEES được định nghĩa như sau:

SQL
CREATE TABLE employees (
   employee_id NUMBER           NOT NULL,
   first_name    VARCHAR2(1000) NOT NULL,
   last_name     VARCHAR2(1000) NOT NULL,
   date_of_birth DATE           NOT NULL,
   phone_number VARCHAR2(1000) NOT NULL,
   CONSTRAINT employees_pk PRIMARY KEY (employee_id)
);

Database tự động tạo index cho primary key. Điều đó có nghĩa có index trên column EMPLOYEE_ID, dù không có create index statement.

Query sau dùng primary key để lấy tên của một nhân viên:

SQL
SELECT first_name, last_name
  FROM employees
 WHERE employee_id = 123

Where clause không thể match nhiều row vì primary key constraint bảo đảm tính duy nhất của các value EMPLOYEE_ID. Database không cần đi theo index leaf node — chỉ cần traverse index tree. Chúng ta có thể dùng execution plan để xác minh:

Execution plan của Oracle cho thấy INDEX UNIQUE SCAN - operation chỉ traverse index tree. Operation này tận dụng đầy đủ logarithmic scalability của index để tìm entry rất nhanh, gần như không phụ thuộc vào kích thước table.

Mẹo

Execution plan (đôi khi gọi là explain plan hoặc query plan) cho biết các bước database thực hiện để chạy một SQL statement. Appendix A ở trang 165 giải thích cách lấy và đọc execution plan trong các database khác.

Sau khi access index, database phải thực hiện thêm một bước để lấy dữ liệu được query (FIRST_NAME, LAST_NAME) từ table storage: operation TABLE ACCESS BY INDEX ROWID. Operation này có thể trở thành bottleneck về performance, như đã giải thích trong “Slow Indexes, Part I”, nhưng không có rủi ro đó khi dùng INDEX UNIQUE SCAN. Operation này không thể trả về quá một entry nên không thể kích hoạt quá một lần table access. Điều đó nghĩa là các yếu tố tạo nên một query chậm không xuất hiện với INDEX UNIQUE SCAN.

Primary Key Không Có Unique Index#

Primary key không nhất thiết phải cần unique index - bạn cũng có thể dùng non-unique index. Trong trường hợp đó, Oracle database không dùng INDEX UNIQUE SCAN mà dùng operation INDEX RANGE SCAN. Tuy vậy, constraint vẫn duy trì tính duy nhất của key, nên index lookup trả về nhiều nhất một entry.

Một lý do dùng non-unique index cho primary key là deferrable constraint. Khác với regular constraint được validate trong khi execute statement, database hoãn việc validate deferrable constraint cho đến khi transaction được commit. Deferred constraint cần thiết để insert dữ liệu vào các table có circular dependency.

Concatenated Index#

Dù database tự động tạo index cho primary key, vẫn có chỗ để tinh chỉnh thủ công nếu key gồm nhiều column. Trong trường hợp đó, database tạo index trên tất cả primary key column - gọi là concatenated index (còn gọi là multicolumn, composite hoặc combined index). Lưu ý rằng thứ tự column của concatenated index ảnh hưởng lớn đến khả năng sử dụng, nên phải được chọn cẩn thận.

Để minh họa, giả sử có một vụ sáp nhập công ty. Nhân viên của công ty kia được thêm vào table EMPLOYEES của chúng ta, khiến table lớn gấp mười lần. Chỉ có một vấn đề: EMPLOYEE_ID không còn duy nhất trên cả hai công ty. Chúng ta cần extend primary key bằng một identifier bổ sung, chẳng hạn subsidiary ID. Vì vậy primary key mới có hai column: EMPLOYEE_ID như trước và SUBSIDIARY_ID để khôi phục tính duy nhất.

Vì vậy, index cho primary key mới được định nghĩa như sau:

SQL
CREATE UNIQUE INDEX employee_pk
    ON employees (employee_id, subsidiary_id);

Query cho một nhân viên cụ thể phải xét đến toàn bộ primary key, tức là cũng phải dùng column SUBSIDIARY_ID:

SQL
SELECT first_name, last_name
  FROM employees
 WHERE employee_id = 123
   AND subsidiary_id = 30;

Execution time tăng theo kích thước table: nếu table tăng gấp mười lần, FULL TABLE SCAN mất thời gian gấp mười lần. Nguy hiểm của operation này là nó thường đủ nhanh trong development environment nhỏ, nhưng lại gây vấn đề performance nghiêm trọng trong production.

Full Table Scan#

Operation TABLE ACCESS FULL, còn gọi là full table scan, vẫn có thể là operation hiệu quả nhất trong một số trường hợp, đặc biệt khi lấy một phần lớn table.

Điều này một phần do overhead của chính index lookup, vốn không có với operation TABLE ACCESS FULL. Chủ yếu là vì index lookup đọc từng block một, do database không biết block nào cần đọc tiếp theo cho đến khi block hiện tại đã được xử lý. FULL TABLE SCAN dù sao cũng phải lấy toàn bộ table, nên database có thể đọc các chunk lớn hơn mỗi lần (multi block read). Dù database đọc nhiều dữ liệu hơn, nó có thể cần thực hiện ít read operation hơn.

Database không dùng index vì không thể tùy ý dùng từng column riêng lẻ từ một concatenated index. Quan sát kỹ cấu trúc index sẽ làm rõ điều này.

Concatenated index cũng chỉ là B-tree index như mọi index khác, lưu dữ liệu đã index trong một list được sắp xếp. Database xét từng column theo vị trí của nó trong định nghĩa index để sắp xếp các index entry. Column đầu tiên là sort criterion chính, còn column thứ hai chỉ quyết định thứ tự nếu hai entry có cùng value ở column đầu tiên, và cứ như vậy.

Quan trọng

Concatenated index là một index trải trên nhiều column.

Vì thế, thứ tự của index hai column giống thứ tự của danh bạ điện thoại: trước hết sắp theo họ, rồi theo tên. Điều đó nghĩa là index hai column không hỗ trợ tìm chỉ theo column thứ hai; việc đó giống như tìm danh bạ điện thoại theo tên.

Đoạn trích index trong Hình 2.1 cho thấy các entry của subsidiary 20 không được lưu cạnh nhau. Cũng thấy rõ không có entry nào có SUBSIDIARY_ID = 20 trong tree, dù chúng tồn tại ở leaf node. Do đó tree không hữu ích cho query này.

Mẹo

Hình dung index giúp hiểu index hỗ trợ những query nào. Bạn có thể query database để lấy các entry theo thứ tự index (cú pháp SQL:2008, xem trang 144 về các giải pháp proprietary dùng LIMIT, TOP hoặc ROWNUM):

SQL
SELECT <INDEX COLUMN LIST>
  FROM <TABLE>
 ORDER BY <INDEX COLUMN LIST>
 FETCH FIRST 100 ROWS ONLY;

Mẹo

Nếu đưa định nghĩa index và tên table vào query, bạn sẽ nhận được một mẫu từ index. Hãy tự hỏi các row được yêu cầu có được nhóm ở một vị trí tập trung không. Nếu không, index tree không thể giúp tìm vị trí đó.

Dĩ nhiên, chúng ta có thể thêm một index khác trên SUBSIDIARY_ID để cải thiện tốc độ query. Tuy nhiên có một giải pháp tốt hơn, ít nhất nếu giả sử việc tìm chỉ bằng EMPLOYEE_ID không có ý nghĩa.

Chúng ta có thể tận dụng thực tế rằng column index đầu tiên luôn dùng được để tìm kiếm. Một lần nữa, nó giống danh bạ điện thoại: bạn không cần biết tên để tìm theo họ. Mẹo là đảo thứ tự column index để SUBSIDIARY_ID ở vị trí đầu tiên:

SQL
CREATE UNIQUE INDEX EMPLOYEES_PK
    ON EMPLOYEES (SUBSIDIARY_ID, EMPLOYEE_ID);

Hai column kết hợp vẫn là duy nhất, nên query với toàn bộ primary key vẫn có thể dùng INDEX UNIQUE SCAN, nhưng chuỗi index entry đã hoàn toàn khác. SUBSIDIARY_ID trở thành sort criterion chính. Điều đó nghĩa là mọi entry của một subsidiary nằm liên tiếp trong index, nên database có thể dùng B-tree để tìm vị trí của chúng.

Quan trọng

Điểm quan trọng nhất khi định nghĩa concatenated index là chọn thứ tự column sao cho index có thể được dùng thường xuyên nhất.

Execution plan xác nhận database dùng index “đảo ngược”. Chỉ SUBSIDIARY_ID không còn duy nhất, nên database phải đi theo các leaf node để tìm mọi entry match: vì vậy nó dùng operation INDEX RANGE SCAN.

Nói chung, database có thể dùng concatenated index khi tìm bằng các column dẫn đầu (bên trái nhất). Index có ba column có thể dùng khi tìm column đầu tiên, khi tìm hai column đầu tiên cùng nhau, và khi tìm bằng tất cả column.

Dù giải pháp hai index cũng cho select performance rất tốt, giải pháp một index vẫn được ưu tiên. Nó không chỉ tiết kiệm storage space mà còn giảm maintenance overhead cho index thứ hai. Table càng ít index thì performance của insert, delete và update càng tốt.

Để định nghĩa index tối ưu, bạn phải hiểu không chỉ cách index hoạt động mà còn phải biết application query dữ liệu thế nào. Điều đó nghĩa là phải biết các tổ hợp column xuất hiện trong where clause.

Vì vậy, định nghĩa index tối ưu rất khó với external consultant vì họ không có cái nhìn tổng thể về access path của application. Consultant thường chỉ có thể xét một query. Họ không khai thác lợi ích bổ sung mà index có thể mang lại cho các query khác. Database administrator cũng ở vị trí tương tự vì họ có thể biết database schema nhưng không có insight sâu về access path.

Nơi duy nhất kiến thức kỹ thuật về database gặp kiến thức chức năng về business domain là bộ phận development. Developer hiểu dữ liệu và biết access path. Họ có thể đánh index đúng để đem lại lợi ích tốt nhất cho toàn bộ application mà không cần nhiều công sức.

Index Chậm, Phần II#

Phần trước đã giải thích cách thu được lợi ích bổ sung từ index hiện có bằng cách thay đổi thứ tự column, nhưng ví dụ chỉ xét hai SQL statement. Tuy nhiên, thay đổi index có thể ảnh hưởng đến mọi query trên table được index. Phần này giải thích cách database chọn index và minh họa các side effect có thể xảy ra khi thay đổi index hiện có.

Index EMPLOYEE_PK đã dùng cải thiện performance của mọi query chỉ tìm theo subsidiary. Tuy vậy, nó có thể dùng cho mọi query tìm theo SUBSIDIARY_ID, bất kể có thêm search criteria nào không. Điều đó nghĩa là index trở nên dùng được cho các query vốn dùng index khác với một phần khác của where clause. Trong trường hợp đó, nếu có nhiều access path khả dụng, optimizer có nhiệm vụ chọn access path tốt nhất.

Query Optimizer

Query optimizer, hay query planner, là component của database biến SQL statement thành execution plan. Quá trình này cũng gọi là compiling hoặc parsing. Có hai loại optimizer riêng biệt.

Cost-based optimizer (CBO) tạo nhiều biến thể execution plan và tính một cost value cho từng plan. Việc tính cost dựa trên các operation đang dùng và số row được estimate. Cuối cùng, cost value làm chuẩn để chọn execution plan “tốt nhất”.

Rule-based optimizer (RBO) tạo execution plan bằng một tập rule hard-coded. Rule-based optimizer ít linh hoạt hơn và ngày nay hiếm khi được dùng.

Thay đổi index cũng có thể có side effect khó chịu. Trong ví dụ của chúng ta, application danh bạ điện thoại nội bộ đã chậm đi rất nhiều từ sau vụ sáp nhập. Phân tích đầu tiên xác định query sau là nguyên nhân làm chậm:

SQL
SELECT first_name, last_name, subsidiary_id, phone_number
  FROM employees
 WHERE last_name = 'WINAND'
   AND subsidiary_id = 30;

Tuy nhiên, đáng nghi là nó dùng index chúng ta vừa thay đổi; đó là lý do đủ để nghi ngờ thay đổi index gây ra vấn đề performance, nhất là khi nhớ định nghĩa index cũ bắt đầu bằng column EMPLOYEE_ID, vốn hoàn toàn không nằm trong where clause. Trước đây query không thể dùng index đó.

SQL
SELECT /*+ NO_INDEX(EMPLOYEES EMPLOYEE_PK) */

Trong những trường hợp như vậy, tốt nhất là lần lượt xem từng bước của execution plan có vấn đề. Bước đầu là INDEX RANGE SCAN trên index EMPLOYEES_PK. Index đó không cover column LAST_NAME; INDEX RANGE SCAN chỉ có thể xét filter SUBSIDIARY_ID. Oracle database cho thấy điều này trong khu vực “Predicate Information”, entry “2” của execution plan. Tại đó có thể thấy các điều kiện được áp dụng cho từng operation.

Mẹo

Appendix A, “Execution Plans”, giải thích cách tìm “Predicate Information” cho các database khác.

INDEX RANGE SCAN có operation ID 2 (Ví dụ 2.1 ở trang 19) chỉ áp dụng filter SUBSIDIARY_ID=30. Điều đó nghĩa là nó traverse index tree để tìm entry đầu tiên có SUBSIDIARY_ID 30. Sau đó nó đi theo leaf node chain để tìm mọi entry khác của subsidiary đó. Kết quả của INDEX RANGE SCAN là list ROWID thỏa điều kiện SUBSIDIARY_ID: tùy quy mô subsidiary, có thể chỉ có vài ROWID hoặc có thể có hàng trăm.

Bước tiếp theo là operation TABLE ACCESS BY INDEX ROWID. Nó dùng ROWID từ bước trước để lấy các row, tức mọi column, từ table. Khi column LAST_NAME đã có, database mới có thể đánh giá phần còn lại của where clause. Điều đó nghĩa là database phải lấy mọi row có SUBSIDIARY_ID=30 trước khi có thể áp dụng filter LAST_NAME.

Response time của statement không phụ thuộc vào kích thước result set mà phụ thuộc vào số nhân viên trong subsidiary cụ thể. Nếu subsidiary chỉ có vài thành viên, INDEX RANGE SCAN có performance tốt hơn. Tuy vậy, TABLE ACCESS FULL có thể nhanh hơn với subsidiary rất lớn vì nó có thể đọc phần lớn table trong một lần (xem “Full Table Scan” ở trang 13).

Query chậm vì index lookup trả về nhiều ROWID, một cho mỗi nhân viên của công ty ban đầu, và database phải lấy chúng riêng lẻ. Đây là sự kết hợp hoàn hảo của hai yếu tố làm index chậm: database đọc một index range rộng và phải lấy nhiều row riêng lẻ.

Việc chọn execution plan tốt nhất cũng phụ thuộc vào data distribution của table, nên optimizer dùng statistics về nội dung database. Trong ví dụ này, một histogram chứa distribution nhân viên theo subsidiary được dùng. Điều này cho phép optimizer estimate số row trả về từ index lookup; kết quả được dùng để tính cost.

Statistics

Cost-based optimizer dùng statistics về table, column và index. Phần lớn statistics được thu thập ở cấp column: số lượng value riêng biệt, value nhỏ nhất và lớn nhất (data range), số lần xuất hiện NULL và column histogram (data distribution). Value statistics quan trọng nhất của table là kích thước của nó (theo row và block).

Statistics index quan trọng nhất là tree depth, số leaf node, số distinct key và clustering factor (xem Chương 5, “Clustering Data”).

Optimizer dùng các value này để estimate selectivity của các predicate trong where clause.

Nếu không có statistics, chẳng hạn vì chúng đã bị xóa, optimizer dùng các value mặc định. Statistics mặc định của Oracle database cho thấy index nhỏ với selectivity trung bình. Chúng dẫn đến estimate rằng INDEX RANGE SCAN sẽ trả về 40 row. Execution plan hiển thị estimate này trong column Rows (một lần nữa, xem Ví dụ 2.1 ở trang 19). Rõ ràng đây là estimate thấp hơn rất nhiều, vì có 1000 nhân viên làm việc cho subsidiary này.

Nếu cung cấp statistics chính xác, optimizer làm việc tốt hơn. Execution plan sau cho thấy estimate mới: 1000 row cho INDEX RANGE SCAN. Vì thế optimizer tính cost value cao hơn cho table access tiếp theo.

Functions#

Index trên LAST_NAME đã cải thiện performance đáng kể, nhưng nó yêu cầu bạn tìm kiếm bằng đúng chữ hoa/chữ thường như được lưu trong database. Phần này giải thích cách bỏ hạn chế này mà không làm giảm performance.

Lưu ý

MySQL 5.6 không hỗ trợ function-based indexing như mô tả bên dưới. Thay vào đó, virtual column từng được lên kế hoạch cho MySQL 6.0 nhưng chỉ được giới thiệu trong MariaDB 5.2.

Tìm Kiếm Không Phân Biệt Hoa Thường Bằng UPPER hoặc LOWER#

Bỏ qua chữ hoa/chữ thường trong where clause rất đơn giản. Chẳng hạn, bạn có thể chuyển cả hai vế so sánh thành ký hiệu toàn chữ hoa:

SQL
SELECT first_name, last_name, phone_number
  FROM employees
 WHERE UPPER(last_name) = UPPER('winand');

Dù search term hoặc column LAST_NAME dùng kiểu viết hoa nào, function UPPER vẫn làm chúng match như mong muốn.

Lưu ý

Một cách khác để match không phân biệt hoa thường là dùng “collation” khác. Collation mặc định của SQL Server và MySQL không phân biệt chữ hoa và chữ thường, chúng mặc định case-insensitive.

Execution plan

Logic của query này hoàn toàn hợp lý nhưng execution plan thì không.

Chúng ta lại gặp người bạn cũ full table scan. Dù có index trên LAST_NAME, index đó không dùng được vì việc tìm kiếm không diễn ra trên LAST_NAME mà trên UPPER(LAST_NAME). Theo góc nhìn của database, đây là hai thứ hoàn toàn khác nhau.

Đây là cái bẫy mà tất cả chúng ta có thể gặp phải. Chúng ta nhận ra ngay quan hệ giữa LAST_NAME và UPPER(LAST_NAME) và mong database cũng “thấy” như vậy. Trên thực tế, góc nhìn của optimizer giống thế này hơn:

SQL
SELECT first_name, last_name, phone_number
  FROM employees
 WHERE BLACKBOX(...) = 'WINAND';

Function UPPER chỉ là một black box. Các parameter của function không liên quan vì không có quan hệ tổng quát nào giữa parameter của function và kết quả.

Mẹo

Hãy thay tên function bằng BLACKBOX để hiểu góc nhìn của optimizer.

Đánh Giá Khi Compile

Optimizer có thể đánh giá expression ở vế phải trong “compile time” vì nó có tất cả input parameter. Vì vậy execution plan của Oracle (phần “Predicate Information”) chỉ hiển thị ký hiệu chữ hoa của search term. Hành vi này rất giống compiler đánh giá constant expression trong compile time.

Để hỗ trợ query đó, chúng ta cần một index cover search term thực tế. Điều đó nghĩa là không cần index trên LAST_NAME mà trên UPPER(LAST_NAME):

SQL
CREATE INDEX emp_up_name
    ON employees (UPPER(last_name));

Index có định nghĩa chứa function hoặc expression được gọi là function-based index (FBI). Thay vì sao chép trực tiếp dữ liệu column vào index, function-based index áp dụng function trước rồi đưa kết quả vào index. Do đó index lưu tên ở dạng toàn chữ hoa.

Database có thể dùng function-based index nếu expression chính xác của định nghĩa index xuất hiện trong SQL statement, như ví dụ trên. Execution plan xác nhận điều này:

Cảnh báo

Đôi khi ORM tool dùng UPPER và LOWER mà developer không biết. Ví dụ, Hibernate insert LOWER ngầm cho các tìm kiếm không phân biệt hoa thường.

Số row được xử lý cho mỗi operation (cardinality estimate) là con số đặc biệt quan trọng, cũng được hiển thị trong execution plan của SQL Server và PostgreSQL.

Oracle Statistics cho Function-Based Index

Oracle database duy trì thông tin về số distinct column value như một phần của table statistics. Các con số này được dùng lại nếu column là một phần của nhiều index.

Statistics cho function-based index (FBI) cũng được lưu ở cấp table dưới dạng virtual column. Dù Oracle database tự động thu thập index statistics cho index mới (từ release 10g), nó không update table statistics. Vì vậy, tài liệu Oracle khuyến nghị update table statistics sau khi tạo function-based index:

User-Defined Function#

Function-based indexing là cách tiếp cận rất tổng quát. Ngoài function như UPPER, bạn còn có thể index expression như A + B và thậm chí dùng user-defined function trong định nghĩa index.

Có một ngoại lệ quan trọng. Chẳng hạn, không thể reference current time trong định nghĩa index, trực tiếp hay gián tiếp, như ví dụ sau.

CREATE FUNCTION get_age(date_of_birth DATE)
RETURN NUMBER
AS
BEGIN
   RETURN
     TRUNC(MONTHS_BETWEEN(SYSDATE, date_of_birth)/12);
END;
/

Function GET_AGE dùng ngày hiện tại (SYSDATE) để tính tuổi dựa trên ngày sinh được cung cấp. Bạn có thể dùng function này ở mọi phần của SQL query, ví dụ trong select và where clause:

SQL
SELECT first_name, last_name, get_age(date_of_birth)
  FROM employees
 WHERE get_age(date_of_birth) = 42;

Query liệt kê mọi nhân viên 42 tuổi. Dùng function-based index là ý tưởng hiển nhiên để tối ưu query này, nhưng bạn không thể dùng function GET_AGE trong định nghĩa index vì nó không deterministic. Điều đó nghĩa là kết quả của function call không hoàn toàn được quyết định bởi parameter của nó. Chỉ function luôn trả về cùng kết quả cho cùng parameter, tức function deterministic, mới có thể được index.

Lý do cho hạn chế này đơn giản. Khi insert row mới, database gọi function và lưu kết quả trong index, rồi kết quả đó nằm yên, không đổi. Không có process định kỳ nào update index. Database chỉ update tuổi đã index khi ngày sinh bị thay đổi bằng update statement. Sau sinh nhật tiếp theo, tuổi được lưu trong index sẽ sai.

Ngoài việc phải deterministic, PostgreSQL và Oracle database yêu cầu function được khai báo deterministic khi dùng trong index, nên bạn phải dùng keyword DETERMINISTIC (Oracle) hoặc IMMUTABLE (PostgreSQL).

Cẩn trọng

PostgreSQL và Oracle database tin vào khai báo DETERMINISTIC hoặc IMMUTABLE, nghĩa là chúng tin developer. Bạn có thể khai báo function GET_AGE là deterministic và dùng nó trong định nghĩa index. Bất kể khai báo đó, nó sẽ không hoạt động như dự định vì tuổi lưu trong index sẽ không tăng theo năm tháng; nhân viên sẽ không già đi, ít nhất là trong index.

Các ví dụ khác về function không thể được “index” là random number generator và function phụ thuộc environment variable.

Over-Indexing#

Nếu khái niệm function-based indexing còn mới, bạn có thể bị cám dỗ index mọi thứ, nhưng thực tế đây là điều cuối cùng bạn nên làm. Lý do là mọi index đều tạo ra maintenance liên tục. Function-based index đặc biệt rắc rối vì chúng khiến việc tạo index dư thừa rất dễ dàng.

Tìm kiếm không phân biệt hoa thường ở trên cũng có thể triển khai bằng function LOWER:

SQL
SELECT first_name, last_name, phone_number
  FROM employees
 WHERE LOWER(last_name) = LOWER('winand');

Một index không thể hỗ trợ cả hai cách bỏ qua chữ hoa thường. Dĩ nhiên, chúng ta có thể tạo index thứ hai trên LOWER(last_name) cho query này, nhưng điều đó nghĩa là database phải duy trì hai index cho mỗi statement insert, update và delete (xem thêm Chương 8, “Modifying Data”). Để một index là đủ, bạn nên dùng nhất quán cùng một function trong toàn application.

Mẹo

Hợp nhất access path để một index có thể được dùng bởi nhiều query.

Mẹo

Luôn hướng đến việc index dữ liệu gốc vì đó thường là thông tin hữu ích nhất có thể đưa vào index.

Parameterized Queries#

Phần này đề cập đến một chủ đề bị bỏ qua trong phần lớn textbook về SQL: parameterized query và bind parameter.

Bind parameter, còn gọi là dynamic parameter hoặc bind variable, là một cách khác để truyền dữ liệu vào database. Thay vì đặt value trực tiếp vào SQL statement, bạn chỉ cần dùng một placeholder như ?, :name hoặc @name rồi cung cấp value thực qua một API call riêng.

Không có gì sai khi viết value trực tiếp vào các ad-hoc statement; tuy nhiên, có hai lý do chính đáng để dùng bind parameter trong program:

Database có execution plan cache như SQL Server và Oracle database có thể tái sử dụng execution plan khi execute cùng một statement nhiều lần. Cách này tiết kiệm công sức xây dựng lại execution plan, nhưng chỉ hoạt động khi SQL statement hoàn toàn giống nhau. Nếu đặt các value khác nhau vào SQL statement, database sẽ xử lý nó như một statement khác và tạo lại execution plan.

Khi dùng bind parameter, bạn không viết value thực mà thay vào đó insert placeholder vào SQL statement. Nhờ vậy, statement không thay đổi khi được execute với các value khác nhau.

Do đó, bước tính cost tiếp theo sẽ cho ra hai cost value khác nhau. Khi optimizer cuối cùng chọn execution plan, nó chọn plan có cost value thấp nhất. Với subsidiary nhỏ hơn, đó là plan dùng index.

Cost của operation TABLE ACCESS BY INDEX ROWID rất nhạy với row count estimate. Chọn số row nhiều gấp mười lần sẽ làm cost value tăng theo hệ số đó. Khi ấy overall cost dùng index còn cao hơn full table scan. Vì vậy, optimizer sẽ chọn execution plan còn lại cho subsidiary lớn hơn.

Khi dùng bind parameter, optimizer không có value cụ thể để xác định frequency của chúng. Nó chỉ giả định distribution đồng đều và luôn nhận được cùng row count estimate và cost value. Cuối cùng, nó sẽ luôn chọn cùng một execution plan.

Mẹo

Column histogram hữu ích nhất khi các value không được distribute đồng đều.

Với column có distribution đồng đều, thường chỉ cần chia số value distinct cho số row trong table. Phương pháp này cũng hoạt động khi dùng bind parameter.

Nếu so optimizer với compiler, bind variable giống như program variable, còn khi viết value trực tiếp vào statement thì chúng giống constant hơn. Database có thể dùng các value từ SQL statement trong lúc optimization, cũng như compiler có thể evaluate constant expression trong lúc compilation. Nói ngắn gọn, bind parameter không visible với optimizer, giống như runtime value của variable không được compiler biết đến.

Từ góc nhìn này, có một nghịch lý nhỏ: bind parameter có thể cải thiện performance nếu không dùng bind parameter cho phép optimizer luôn chọn execution plan tốt nhất. Nhưng cái giá là gì? Việc generate và evaluate mọi execution plan variant là một effort rất lớn, không đáng nếu cuối cùng bạn vẫn nhận cùng một kết quả.

Mẹo

Không dùng bind parameter cũng giống như compile lại một program mỗi lần.

Quyết định xây dựng specialized execution plan hay generic execution plan đặt database trước một dilemma. Hoặc database bỏ effort để evaluate mọi plan variant có thể có ở mỗi lần execution nhằm luôn có execution plan tốt nhất, hoặc tiết kiệm optimization overhead và dùng cached execution plan bất cứ khi nào có thể, chấp nhận rủi ro dùng execution plan suboptimal. Vấn đề là database không biết full optimization cycle có tạo ra một execution plan khác hay không nếu chưa thực sự thực hiện full optimization. Database vendor cố giải quyết dilemma này bằng các heuristic method, nhưng thành công rất hạn chế.

Ở vai trò developer, bạn có thể chủ động dùng bind parameter để giúp giải quyết dilemma này. Cụ thể, bạn nên luôn dùng bind parameter, ngoại trừ những value cần ảnh hưởng đến execution plan.

Status code distribution không đồng đều như “todo” và “done” là một ví dụ tốt. Số entry “done” thường nhiều hơn record “todo” cả một order of magnitude. Trong trường hợp đó, dùng index chỉ có ý nghĩa khi tìm entry “todo”. Partitioning là một ví dụ khác, tức là chia table và index trên nhiều storage area. Khi đó, value thực có thể ảnh hưởng đến partition nào phải được scan. Performance của LIKE query cũng có thể bị ảnh hưởng bởi bind parameter, như chúng ta sẽ thấy trong phần tiếp theo.

Mẹo

Trên thực tế, chỉ có một vài trường hợp mà value thực ảnh hưởng đến execution plan. Vì vậy, nếu còn phân vân, bạn nên dùng bind parameter, chỉ để ngăn SQL injection.

Searching for Ranges#

Các inequality operator như <, > và between có thể dùng index giống như equals operator đã giải thích ở trên. Ngay cả LIKE filter cũng có thể, trong một số điều kiện, dùng index như range condition.

Việc dùng các operation này giới hạn lựa chọn về thứ tự column trong multicolumn index. Giới hạn này thậm chí có thể loại bỏ mọi option indexing tối ưu, vì có những query mà bạn đơn giản không thể định nghĩa một thứ tự column “đúng”.

Greater, Less and BETWEEN#

Câu hỏi này dễ trả lời nếu SQL statement nêu rõ start condition và stop condition:

SQL
SELECT first_name, last_name, date_of_birth
  FROM employees
 WHERE date_of_birth >= TO_DATE(?, 'YYYY-MM-DD')
   AND date_of_birth <= TO_DATE(?, 'YYYY-MM-DD')

Index trên DATE_OF_BIRTH chỉ được scan trong range đã chỉ định. Scan bắt đầu ở date thứ nhất và kết thúc ở date thứ hai. Chúng ta không thể thu hẹp scanned index range thêm nữa.

Start condition và stop condition khó thấy hơn khi có thêm column thứ hai:

SQL
SELECT first_name, last_name, date_of_birth
  FROM employees
 WHERE date_of_birth >= TO_DATE(?, 'YYYY-MM-DD')
   AND date_of_birth <= TO_DATE(?, 'YYYY-MM-DD')
   AND subsidiary_id = ?

Dĩ nhiên, index lý tưởng phải cover cả hai column, nhưng câu hỏi là thứ tự nào?

Các figure sau cho thấy thứ tự column ảnh hưởng thế nào đến scanned index range. Trong minh họa này, chúng ta tìm tất cả nhân viên của subsidiary 27 sinh trong khoảng từ ngày 1 tháng 1 đến ngày 9 tháng 1 năm 1971.

Hình 2.2 mô tả chi tiết một index trên DATE_OF_BIRTH và SUBSIDIARY_ID, theo đúng thứ tự đó. Database sẽ bắt đầu đi theo leaf node chain ở đâu, hay nói cách khác, tree traversal sẽ kết thúc ở đâu?

Index được sắp xếp theo birth date trước. Chỉ khi hai nhân viên sinh cùng ngày thì SUBSIDIARY_ID mới được dùng để sắp xếp các record đó. Tuy nhiên, query bao phủ một date range. Vì vậy, thứ tự của SUBSIDIARY_ID vô dụng trong tree traversal. Điều này trở nên rõ ràng nếu nhận ra rằng không có entry cho subsidiary 27 trong branch node, dù có entry như vậy trong leaf node. Do đó, filter trên DATE_OF_BIRTH là điều kiện duy nhất giới hạn scanned index range. Scan bắt đầu từ entry đầu tiên match date range và kết thúc ở entry cuối cùng, tức toàn bộ năm leaf node được hiển thị trong Hình 2.2.

Bức tranh hoàn toàn khác khi đảo thứ tự column. Hình 2.3 minh họa scan khi index bắt đầu bằng column SUBSIDIARY_ID.

Điểm khác biệt là equals operator giới hạn column index đầu tiên vào một value duy nhất. Trong range của value này (SUBSIDIARY_ID 27), index được sắp xếp theo column thứ hai, tức date of birth, nên không cần đi qua leaf node đầu tiên vì branch node đã cho biết không có employee nào của subsidiary 27 sinh sau ngày 25 tháng 6 năm 1969 trong leaf node đầu tiên.

Tree traversal dẫn trực tiếp đến leaf node thứ hai. Trong trường hợp này, mọi điều kiện của where clause đều giới hạn scanned index range, nên scan kết thúc ngay tại leaf node đó.

Mẹo

Quy tắc kinh nghiệm: index cho equality trước, rồi đến range.

Performance difference thực tế phụ thuộc vào data và search criteria. Difference có thể không đáng kể nếu filter trên DATE_OF_BIRTH tự nó đã rất selective. Date range càng lớn thì performance difference càng lớn.

Với ví dụ này, chúng ta cũng có thể bác bỏ myth rằng column có selectivity cao nhất phải nằm ở vị trí ngoài cùng bên trái của index. Nếu nhìn vào các figure và chỉ xét selectivity của column đầu tiên, ta thấy cả hai điều kiện đều match 13 record. Điều này đúng bất kể filter chỉ theo DATE_OF_BIRTH hay chỉ theo SUBSIDIARY_ID. Selectivity không có ích ở đây, nhưng một thứ tự column vẫn tốt hơn thứ tự còn lại.

Để tối ưu performance, việc biết scanned index range rất quan trọng. Với phần lớn database, bạn thậm chí có thể thấy range này trong execution plan, chỉ cần biết phải tìm gì. Execution plan sau của Oracle database chỉ rõ rằng index EMP_TEST bắt đầu bằng column DATE_OF_BIRTH.

Indexing LIKE Filters#

SQL LIKE operator rất thường gây ra behavior performance bất ngờ vì một số search term ngăn database dùng index hiệu quả. Điều đó nghĩa là có search term được index rất tốt, nhưng có search term thì không. Vị trí của wildcard character tạo ra toàn bộ khác biệt.

Ví dụ sau dùng wildcard % ở giữa search term:

SQL
SELECT first_name, last_name, date_of_birth
  FROM employees
 WHERE UPPER(last_name) LIKE 'WIN%D'

LIKE filter chỉ có thể dùng các character trước wildcard đầu tiên trong lúc tree traversal. Các character còn lại chỉ là filter predicate và không thu hẹp scanned index range. Vì vậy, một LIKE expression có thể chứa hai loại predicate: (1) phần trước wildcard đầu tiên là access predicate; (2) các character còn lại là filter predicate.

Cẩn trọng

Với PostgreSQL database, bạn có thể cần chỉ định operator class (ví dụ varchar_pattern_ops) để dùng LIKE expression làm access predicate. Xem “Operator Classes and Operator Families” trong tài liệu PostgreSQL để biết thêm chi tiết.

Prefix trước wildcard đầu tiên càng selective thì scanned index range càng nhỏ. Đổi lại, index lookup càng nhanh. Hình 2.4 minh họa quan hệ này bằng ba LIKE expression khác nhau. Cả ba đều chọn cùng một row, nhưng scanned index range, và do đó performance, rất khác nhau.

Expression đầu tiên có hai character trước wildcard. Chúng giới hạn scanned index range còn 18 row. Chỉ một row trong số đó match toàn bộ LIKE expression, còn 17 row kia được fetch rồi loại bỏ. Expression thứ hai có prefix dài hơn, thu hẹp scanned index range còn hai row. Với expression này, database chỉ đọc thêm một row không liên quan đến kết quả. Expression cuối cùng hoàn toàn không có filter predicate: database chỉ đọc entry match toàn bộ LIKE expression.

Quan trọng

Chỉ phần trước wildcard đầu tiên mới đóng vai trò access predicate. Các character còn lại không thu hẹp scanned index range; các entry không match chỉ bị loại khỏi result.

Trường hợp ngược lại cũng có thể xảy ra: LIKE expression bắt đầu bằng wildcard. LIKE expression như vậy không thể làm access predicate. Database phải scan toàn bộ table nếu không có condition khác cung cấp access predicate.

Mẹo

Tránh LIKE expression có leading wildcard, ví dụ '%TERM'.

Vị trí của wildcard character ảnh hưởng đến việc dùng index, ít nhất là trên lý thuyết. Trên thực tế, optimizer tạo generic execution plan khi search term được cung cấp qua bind parameter. Khi đó, optimizer phải đoán liệu phần lớn execution có leading wildcard hay không.

Phần lớn database chỉ giả định rằng không có leading wildcard khi optimize LIKE condition với bind parameter, nhưng giả định này sai nếu LIKE expression được dùng cho full-text search. Đáng tiếc là không có cách trực tiếp để đánh dấu một LIKE condition là full-text search. Box “Labeling Full-Text LIKE Expressions” trình bày một cách thử nhưng không hoạt động. Cách hiển nhiên nhất là chỉ định search term không dùng bind parameter, nhưng điều đó làm tăng optimization overhead và mở ra lỗ hổng SQL injection. Một giải pháp hiệu quả, vẫn secure và portable, là cố ý obfuscate LIKE condition. “Combining Columns” ở trang 70 giải thích chi tiết vấn đề này.

Labeling Full-Text LIKE Expressions

Khi dùng LIKE operator cho full-text search, chúng ta có thể tách wildcard khỏi search term:

SQL
WHERE text_column LIKE '%' || ? || '%'

Wildcard được viết trực tiếp vào SQL statement, nhưng chúng ta dùng bind parameter cho search term. Database tự xây dựng LIKE expression cuối cùng bằng string concatenation operator || (Oracle, PostgreSQL). Dù dùng bind parameter, LIKE expression cuối cùng luôn bắt đầu bằng wildcard. Đáng tiếc là database không nhận ra điều đó.

Với PostgreSQL database, vấn đề khác đi vì PostgreSQL giả định có leading wildcard khi dùng bind parameter cho LIKE expression. PostgreSQL đơn giản là không dùng index trong trường hợp đó. Cách duy nhất để có index access cho LIKE expression là làm cho search term thực tế visible với optimizer.

Nếu không dùng bind parameter mà đặt search term trực tiếp vào SQL statement, bạn phải thực hiện các biện pháp phòng ngừa khác để chống SQL injection attack!

Ngay cả khi database optimize execution plan cho leading wildcard, performance vẫn có thể không đủ. Trong trường hợp đó, bạn có thể dùng phần khác của where clause để access dữ liệu hiệu quả, xem thêm “Index Filter Predicates Used Intentionally” ở trang 112. Nếu không có access path nào khác, bạn có thể dùng một trong các full-text index solution proprietary sau.

Index Merge#

Một trong những câu hỏi phổ biến nhất về indexing là: nên tạo một index cho mỗi column hay một index duy nhất cho tất cả column trong where clause? Trong phần lớn trường hợp, câu trả lời rất đơn giản: một index có nhiều column tốt hơn.

Tuy nhiên, có những query mà một index duy nhất không thể xử lý hoàn hảo, bất kể bạn định nghĩa index thế nào; chẳng hạn query có từ hai range condition độc lập trở lên như ví dụ sau:

SQL
SELECT first_name, last_name, date_of_birth
  FROM employees
 WHERE UPPER(last_name) < ?
   AND date_of_birth    < ?

Không thể định nghĩa B-tree index hỗ trợ query này mà không có filter predicate. Để giải thích, chỉ cần nhớ rằng index là một linked list.

Nếu định nghĩa index là UPPER(LAST_NAME), DATE_OF_BIRTH theo thứ tự đó, list sẽ bắt đầu bằng A và kết thúc bằng Z. Date of birth chỉ được xét khi có hai employee cùng tên. Nếu định nghĩa index theo thứ tự ngược lại, nó sẽ bắt đầu bằng employee lớn tuổi nhất và kết thúc bằng employee trẻ tuổi nhất. Khi đó, name chỉ có ảnh hưởng nhỏ đến sort order.

Dù xoay chuyển định nghĩa index thế nào, các entry vẫn luôn được sắp xếp dọc theo một chain. Một đầu chứa entry nhỏ và đầu kia chứa entry lớn. Vì vậy, index chỉ có thể hỗ trợ một range condition dưới dạng access predicate. Để hỗ trợ hai range condition độc lập cần có trục thứ hai, chẳng hạn như bàn cờ. Query ở trên khi đó sẽ match tất cả entry từ một góc của bàn cờ, nhưng index không giống bàn cờ mà giống một chain. Nó không có góc.

Dĩ nhiên, bạn vẫn có thể chấp nhận filter predicate và dùng multicolumn index. Trong nhiều trường hợp, đó vẫn là giải pháp tốt nhất. Khi đó, định nghĩa index nên đặt column selective hơn lên trước để column này có thể được dùng làm access predicate. Đây có thể là nguồn gốc của myth “most selective first”, nhưng quy tắc này chỉ đúng khi bạn không thể tránh filter predicate.

Lựa chọn còn lại là dùng hai index riêng, mỗi index cho một column. Khi đó database trước tiên phải scan cả hai index rồi kết hợp kết quả.

Lưu ý

Một index scan nhanh hơn hai index scan.

Database dùng hai phương pháp để kết hợp index. Thứ nhất là index join. Chương 4, “The Join Operation”, giải thích chi tiết các related algorithm. Cách thứ hai sử dụng functionality từ thế giới data warehouse.

Data warehouse là mẹ của mọi ad-hoc query. Nó chỉ cần vài cú click để kết hợp các condition tùy ý thành query bạn muốn. Không thể dự đoán những tổ hợp column nào có thể xuất hiện trong where clause, khiến việc indexing như đã giải thích từ đầu gần như không thể.

Data warehouse dùng một loại index chuyên dụng để giải quyết vấn đề đó: bitmap index. Ưu điểm của bitmap index là chúng có thể được kết hợp khá dễ dàng. Vì vậy, bạn có performance khá tốt khi index từng column riêng lẻ. Ngược lại, nếu biết query từ trước để tạo một tailored multicolumn B-tree index, index đó vẫn nhanh hơn việc kết hợp nhiều bitmap index.

Điểm yếu lớn nhất của bitmap index là khả năng scale rất tệ với insert, update và delete. Concurrent write operation gần như không thể thực hiện. Điều đó không thành vấn đề trong data warehouse vì các load process được schedule lần lượt. Trong online application, bitmap index phần lớn là vô dụng.

Quan trọng

Bitmap index gần như không thể dùng cho online transaction processing (OLTP).

Nhiều database product cung cấp giải pháp hybrid giữa B-tree và bitmap index. Khi không có access path tốt hơn, chúng chuyển kết quả của một số B-tree scan thành bitmap structure trong memory. Các structure này có thể được kết hợp hiệu quả. Bitmap structure không được lưu persistent mà bị loại bỏ sau khi statement execute, qua đó tránh vấn đề write scalability kém. Nhược điểm là cần nhiều memory và CPU time. Xét cho cùng, phương pháp này là một hành động tuyệt vọng của optimizer.

Partial Indexes#

Cho đến đây, chúng ta chỉ bàn về những column được thêm vào index. Với partial index (PostgreSQL) hoặc filtered index (SQL Server), bạn cũng có thể chỉ định những row được index.

Cẩn trọng

Oracle database có cách tiếp cận riêng đối với partial indexing. Phần tiếp theo sẽ giải thích cách đó dựa trên phần này.

Partial index hữu ích cho các where condition thường dùng với constant value, chẳng hạn status code trong ví dụ sau:

SQL
SELECT message
  FROM messages
 WHERE processed = 'N'
   AND receiver = ?

Các query như vậy rất phổ biến trong queuing system. Query lấy tất cả message chưa được process của một recipient cụ thể. Message đã được process hiếm khi cần đến. Nếu cần, chúng thường được access bằng một criteria cụ thể hơn như primary key.

Chúng ta có thể optimize query này bằng một two-column index. Chỉ xét query này, thứ tự column không quan trọng vì không có range condition.

SQL
CREATE INDEX messages_todo
          ON messages (receiver, processed)

Index hoàn thành mục đích, nhưng nó chứa nhiều row không bao giờ được tìm kiếm, cụ thể là tất cả message đã được process. Dù vậy, nhờ logarithmic scalability, index vẫn làm query rất nhanh, dù lãng phí nhiều disk space.

Với partial indexing, bạn có thể giới hạn index để chỉ chứa message chưa được process. Syntax cho việc này đơn giản đến bất ngờ: một where clause.

SQL
CREATE INDEX messages_todo
          ON messages (receiver)
       WHERE processed = 'N'

Index chỉ chứa những row thỏa mãn where clause. Trong trường hợp cụ thể này, chúng ta thậm chí có thể bỏ column PROCESSED vì nó luôn là 'N'. Điều đó có nghĩa index giảm kích thước theo hai chiều: theo chiều dọc vì chứa ít row hơn; theo chiều ngang vì đã bỏ một column.

Vì vậy, index rất nhỏ. Với một queue, điều này thậm chí có thể nghĩa là kích thước index không đổi dù table tăng không giới hạn. Index không chứa mọi message, chỉ chứa message chưa được process.

Where clause của partial index có thể phức tạp tùy ý. Giới hạn căn bản duy nhất liên quan đến function: bạn chỉ có thể dùng deterministic function, giống như ở mọi nơi khác trong index definition. Tuy nhiên, SQL Server có rule hạn chế hơn và không cho phép function cũng như OR operator trong index predicate.

Database có thể dùng partial index bất cứ khi nào where clause xuất hiện trong query.

Hãy suy nghĩ

Index nhỏ nhất có đặc điểm gì với query sau?

SQL
SELECT message
  FROM messages
 WHERE processed = 'N';

NULL trong Oracle Database#

NULL trong SQL thường gây nhầm lẫn. Ý tưởng cơ bản của NULL — biểu diễn dữ liệu bị thiếu — khá đơn giản, nhưng có một số điểm đặc biệt. Chẳng hạn, bạn phải dùng IS NULL thay vì = NULL. Oracle database còn có thêm những điểm khác thường về NULL, một mặt vì nó không phải lúc nào cũng xử lý NULL theo đúng standard, mặt khác vì nó xử lý NULL trong index theo một cách rất “đặc biệt”.

SQL standard không định nghĩa NULL là một value mà là placeholder cho một value bị thiếu hoặc chưa biết. Vì vậy, không có value nào có thể là NULL. Thay vào đó, Oracle database xử lý empty string như NULL:

SQL
   SELECT     '0 IS NULL???' AS "what is NULL?" FROM dual
    WHERE      0 IS NULL
UNION ALL
   SELECT    '0 is not null' FROM dual
    WHERE     0 IS NOT NULL
UNION ALL
   SELECT ''''' IS NULL???' FROM dual
    WHERE    '' IS NULL
UNION ALL
   SELECT ''''' is not null' FROM dual
    WHERE    '' IS NOT NULL;
what is NULL?
--------------
0 is not null
'' IS NULL???

Để vấn đề thêm rối, có một trường hợp Oracle database thậm chí xử lý NULL như empty string:

SQL
SELECT dummy
     , dummy || ''
     , dummy || NULL
  FROM dual;
D D D
- - -
X X X

Nối column DUMMY (luôn chứa 'X') với NULL đáng lẽ phải trả về NULL.

Concept NULL được dùng trong nhiều programming language. Dù nhìn ở đâu, empty string cũng không bao giờ là NULL… ngoại trừ trong Oracle database. Trên thực tế, không thể lưu empty string vào field VARCHAR2. Nếu thử làm vậy, Oracle database chỉ lưu NULL.

Điểm đặc biệt này không chỉ kỳ lạ mà còn nguy hiểm. Ngoài ra, điểm khác thường của Oracle database với NULL chưa dừng ở đó — nó tiếp tục ảnh hưởng đến indexing.

Indexing NULL#

Oracle database không đưa row vào index nếu tất cả column được index đều là NULL. Điều đó có nghĩa mọi index đều là một partial index — tương đương với việc có where clause:

SQL
CREATE INDEX idx
          ON tbl (A, B, C, ...)
       WHERE A IS NOT NULL
          OR B IS NOT NULL
          OR C IS NOT NULL
             ...;

Hãy xét index EMP_DOB. Nó chỉ có một column là DATE_OF_BIRTH. Một row không có value DATE_OF_BIRTH sẽ không được thêm vào index này.

SQL
INSERT INTO employees ( subsidiary_id, employee_id
                      , first_name , last_name
                      , phone_number)
               VALUES ( ?, ?, ?, ?, ? );

Insert statement không set DATE_OF_BIRTH nên value mặc định là NULL — vì vậy record không được thêm vào index EMP_DOB. Do đó, index không thể hỗ trợ query tìm các record có DATE_OF_BIRTH IS NULL:

SQL
SELECT first_name, last_name
  FROM employees
 WHERE date_of_birth IS NULL;

Dù bản thân query không cần column index thứ hai, chúng ta thêm một column không bao giờ là NULL để bảo đảm index có đủ mọi row.

Có thể dùng bất kỳ column nào có NOT NULL constraint, chẳng hạn SUBSIDIARY_ID, cho mục đích đó.

Một cách khác là dùng constant expression không bao giờ là NULL. Nhờ vậy, index sẽ có đủ mọi row — kể cả khi DATE_OF_BIRTH là NULL.

SQL
DROP   INDEX emp_dob;
CREATE INDEX emp_dob ON employees (date_of_birth, '1');

Về mặt kỹ thuật, đây là một function-based index. Ví dụ này cũng bác bỏ myth rằng Oracle database không thể index NULL.

Mẹo

Thêm một column không thể là NULL để index NULL như mọi value khác.

NOT NULL Constraints#

Để index một điều kiện IS NULL trong Oracle database, index phải có một column không bao giờ có thể là NULL.

Tuy vậy, chỉ không có entry NULL là chưa đủ. Database phải chắc chắn rằng không bao giờ có entry NULL; nếu không, database phải giả định table có những row không nằm trong index.

Emulating Partial Indexes#

Cách Oracle database xử lý NULL trong index một cách khác thường có thể được dùng để mô phỏng partial index. Để làm vậy, chúng ta chỉ cần dùng NULL cho những row không nên được index.

Để minh họa, chúng ta mô phỏng partial index sau:

SQL
CREATE INDEX messages_todo
          ON messages (receiver)
       WHERE processed = 'N'

Trước tiên, chúng ta cần một function chỉ trả về value RECEIVER khi value PROCESSED là 'N'.

CREATE OR REPLACE
FUNCTION pi_processed(processed CHAR, receiver NUMBER)
RETURN NUMBER
DETERMINISTIC
AS BEGIN
   IF processed IN ('N') THEN
      RETURN receiver;
   ELSE
      RETURN NULL;
   END IF;
END;
/

Function phải deterministic để có thể dùng trong index definition.

Bây giờ chúng ta có thể tạo index chỉ chứa các row có PROCESSED='N'.

SQL
CREATE INDEX messages_todo
          ON messages (pi_processed(processed, receiver));

Để sử dụng index, bạn phải dùng indexed expression trong query:

SQL
SELECT message
  FROM messages
 WHERE pi_processed(processed, receiver) = ?

Obfuscated Conditions#

Các phần sau trình bày một số phương pháp phổ biến để obfuscate condition. Obfuscated condition là where clause được viết theo cách ngăn index được sử dụng đúng mức. Đây là tập hợp các anti-pattern mà mọi developer nên biết và tránh.

Date Types#

Phần lớn obfuscation liên quan đến DATE type. Oracle database đặc biệt dễ gặp vấn đề ở đây vì nó chỉ có một DATE type và type này luôn bao gồm cả time component.

Dùng function TRUNC để loại bỏ time component đã trở thành một practice phổ biến. Thực ra function này không loại bỏ time mà set nó về midnight, vì Oracle database không có pure DATE type. Để bỏ qua time component khi search, bạn có thể dùng function TRUNC ở cả hai phía của phép so sánh — ví dụ để tìm sales của ngày hôm qua:

SQL
SELECT ...
  FROM sales
 WHERE TRUNC(sale_date) = TRUNC(sysdate - INTERVAL '1' DAY)

Đây là một statement hoàn toàn hợp lệ và đúng, nhưng không thể sử dụng đúng mức index trên SALE_DATE. Như đã giải thích trong “Case-Insensitive Search Using UPPER or LOWER” ở trang 24, TRUNC(sale_date) hoàn toàn khác SALE_DATE — function là black box đối với database.

Có một giải pháp khá đơn giản cho vấn đề này: function-based index.

SQL
CREATE INDEX index_name
          ON table_name (TRUNC(sale_date))

Nhưng khi đó bạn phải luôn dùng TRUNC(date_column) trong where clause. Nếu dùng không nhất quán — lúc có, lúc không có TRUNC — bạn sẽ cần hai index!

Vấn đề tương tự cũng xảy ra với database có pure date type nếu bạn search một khoảng thời gian dài hơn, như trong MySQL query sau:

SQL
SELECT ...
  FROM sales
 WHERE DATE_FORMAT(sale_date, "%Y-%M")
     = DATE_FORMAT(now()    , "%Y-%M')

Query dùng date format chỉ chứa year và month: một lần nữa, đây là query hoàn toàn đúng nhưng có cùng vấn đề như trước. Tuy nhiên, giải pháp ở trên không áp dụng được vì MySQL không có function-based index.

Giải pháp thay thế là dùng explicit range condition. Đây là một giải pháp generic hoạt động với mọi database:

SQL
SELECT ...
  FROM sales
 WHERE sale_date BETWEEN quarter_begin(?)
                     AND quarter_end(?)

Nếu đã làm bài tập, có lẽ bạn nhận ra pattern từ exercise về tất cả employee 42 tuổi.

Một index thông thường trên SALE_DATE là đủ để optimize query này. Các function QUARTER_BEGIN và QUARTER_END tính boundary date. Việc tính toán có thể hơi phức tạp vì operator between luôn bao gồm các boundary value. Vì vậy, function QUARTER_END phải trả về một time stamp ngay trước ngày đầu tiên của quarter tiếp theo nếu SALE_DATE có time component. Logic này có thể được ẩn trong function.

Các ví dụ ở những trang sau cho thấy cách implement function QUARTER_BEGIN và QUARTER_END cho nhiều database khác nhau.

MySQL#

CREATE FUNCTION quarter_begin(dt DATETIME)
RETURNS DATETIME DETERMINISTIC
RETURN CONVERT
       (
          CONCAT
          ( CONVERT(YEAR(dt),CHAR(4))
          , '-'
          , CONVERT(QUARTER(dt)*3-2,CHAR(2))
          , '-01'
          )
       , datetime
       );
CREATE FUNCTION quarter_end(dt DATETIME)
RETURNS DATETIME DETERMINISTIC
RETURN DATE_ADD
       ( DATE_ADD ( quarter_begin(dt), INTERVAL 3 MONTH )
       , INTERVAL -1 MICROSECOND);

Oracle Database#

BEGIN

RETURN DATE
AS

   -- the Oracle DATE type has seconds resolution
   -- subtract one second from the first
   -- day of the following quarter

Bạn có thể dùng các auxiliary function tương tự cho những period khác — phần lớn sẽ đơn giản hơn các ví dụ trên, đặc biệt khi dùng condition lớn hơn hoặc bằng (>=) và nhỏ hơn (<) thay cho operator between. Tất nhiên, nếu muốn bạn cũng có thể tính boundary date trong application.

Mẹo

Viết query cho các period liên tục dưới dạng explicit range condition. Hãy làm vậy ngay cả với một ngày — ví dụ, trong Oracle database:

SQL
    sale_date >= TRUNC(sysdate)
AND sale_date < TRUNC(sysdate + INTERVAL '1' DAY)

Một obfuscation phổ biến khác là so sánh date dưới dạng string, như trong PostgreSQL example sau:

SQL
SELECT ...
  FROM sales
 WHERE TO_CHAR(sale_Date, 'YYYY-MM-DD') = '1970-01-01'

Vấn đề một lần nữa là việc convert DATE_COLUMN. Những condition như vậy thường được tạo ra vì nghĩ rằng database chỉ nhận được type number và string. Tuy nhiên, bind parameter hỗ trợ mọi data type. Chẳng hạn, bạn có thể dùng object java.util.Date làm bind parameter. Đây là một lợi ích khác của bind parameter.

Nếu không thể làm vậy, bạn chỉ cần convert search term thay vì table column:

SQL
SELECT ...
  FROM sales
 WHERE sale_date = TO_DATE('1970-01-01', 'YYYY-MM-DD')

Query này có thể dùng một index thông thường trên SALE_DATE. Hơn nữa, nó chỉ convert input string một lần. Statement trước phải convert mọi date được lưu trong table trước khi có thể so sánh chúng với search term.

Dù thay đổi theo cách nào — dùng bind parameter hay convert phía còn lại của phép so sánh — bạn đều có thể dễ dàng tạo bug nếu SALE_DATE có time component. Khi đó, bạn phải dùng explicit range condition:

SQL
SELECT ...
  FROM sales
 WHERE sale_date >= TO_DATE('1970-01-01', 'YYYY-MM-DD')
   AND sale_date < TO_DATE('1970-01-01', 'YYYY-MM-DD')
                  + INTERVAL '1' DAY

Luôn cân nhắc dùng explicit range condition khi so sánh date.

LIKE on Date Types#

Obfuscation sau đây đặc biệt khó nhận ra:

SQL
sale_date LIKE SYSDATE

Thoạt nhìn, nó không giống obfuscation vì không dùng function nào.

Tuy nhiên, operator LIKE bắt buộc phải so sánh string. Tùy database, điều đó có thể gây error hoặc tạo implicit type conversion ở cả hai phía. Phần “Predicate Information” của execution plan cho thấy Oracle database xử lý thế nào:

Execution plan
filter( INTERNAL_FUNCTION(SALE_DATE)
   LIKE TO_CHAR(SYSDATE@!))

Function INTERNAL_FUNCTION convert type của column SALE_DATE. Một tác dụng phụ là nó cũng ngăn việc dùng index thông thường trên DATE_COLUMN, giống như mọi function khác.

Numeric Strings#

Numeric string là number được lưu trong text column. Dù đây là một practice rất tệ, nó không tự động làm index vô dụng nếu bạn nhất quán xử lý value đó như string:

SQL
SELECT ...
  FROM ...
 WHERE numeric_string = '42'

Dĩ nhiên statement này có thể dùng index trên NUMERIC_STRING. Tuy nhiên, nếu so sánh bằng number thì database không còn dùng được condition này làm access predicate.

SQL
SELECT ...
  FROM ...
 WHERE numeric_string = 42

Hãy chú ý dấu nháy bị thiếu. Dù một số database báo error (ví dụ PostgreSQL), nhiều database chỉ thêm implicit type conversion.

SQL
SELECT ...
  FROM ...
 WHERE TO_NUMBER(numeric_string) = 42

Đây là cùng vấn đề như trước. Index trên NUMERIC_STRING không thể dùng được do lời gọi function. Giải pháp cũng giống như trước: đừng convert table column, hãy convert search term.

SQL
SELECT ...
  FROM ...
 WHERE numeric_string = TO_CHAR(42)

Bạn có thể thắc mắc tại sao database không tự làm theo cách này. Lý do là convert string thành number luôn cho một kết quả không mơ hồ. Chiều ngược lại thì không đúng. Một number được format thành text có thể chứa space, punctuation và leading zero. Một value có thể được viết theo nhiều cách:

42
042
0042
00042
...

Database không thể biết number format được dùng trong column NUMERIC_STRING nên nó làm theo chiều ngược lại: database convert string thành number — đây là phép biến đổi không mơ hồ.

Function TO_CHAR chỉ trả về một string representation của number. Vì vậy, nó chỉ match string đầu tiên trong list trên. Nếu dùng TO_NUMBER, nó match tất cả string. Điều đó có nghĩa hai biến thể không chỉ khác nhau về performance mà còn khác nhau về semantic!

Dùng numeric string nhìn chung gây nhiều vấn đề: quan trọng nhất là nó gây performance problem do implicit conversion và tạo rủi ro gặp conversion error vì number không hợp lệ. Ngay cả query đơn giản nhất, không dùng function nào trong where clause, cũng có thể abort với conversion error nếu chỉ cần một invalid number được lưu trong table.

Mẹo

Dùng numeric type để lưu number.

Lưu ý rằng vấn đề không xảy ra theo chiều ngược lại:

SQL
SELECT ...
  FROM ...
 WHERE numeric_number = '42'

Database sẽ nhất quán transform string thành number. Nó không áp dụng function lên column có thể được index, vì vậy regular index vẫn hoạt động. Tuy nhiên, bạn vẫn có thể tự convert theo cách sai:

SQL
SELECT ...
  FROM ...
 WHERE TO_CHAR(numeric_number) = '42'

Combining Columns#

Phần này nói về một obfuscation phổ biến ảnh hưởng đến concatenated index.

Ví dụ đầu tiên lại nói về date và time type nhưng theo chiều ngược lại. MySQL query sau kết hợp một date column và một time column để áp dụng range filter lên cả hai:

SQL
SELECT ...
  FROM ...
 WHERE ADDTIME(date_column, time_column)
     > DATE_ADD(now(), INTERVAL -1 DAY)

Nó chọn mọi record trong 24 giờ vừa qua. Query không thể dùng đúng mức concatenated index trên (DATE_COLUMN, TIME_COLUMN) vì search không thực hiện trên các column được index mà trên derived data.

Bạn có thể tránh vấn đề này bằng data type có cả date và time component (ví dụ MySQL DATETIME). Khi đó, bạn có thể dùng column này mà không cần function call:

SQL
SELECT ...
  FROM ...
 WHERE datetime_column
     > DATE_ADD(now(), INTERVAL -1 DAY)

Đáng tiếc là khi gặp vấn đề này, thường không thể thay đổi table.

Lựa chọn tiếp theo là function-based index nếu database hỗ trợ — dù cách này có mọi drawback đã bàn trước đó. Với MySQL, function-based index vốn không phải là một option.

Tuy vậy, vẫn có thể viết query để database dùng concatenated index trên DATE_COLUMN, TIME_COLUMN với access predicate — ít nhất là một phần. Để làm vậy, chúng ta thêm một condition vào DATE_COLUMN.

SQL
WHERE ADDTIME(date_column, time_column)
    > DATE_ADD(now(), INTERVAL -1 DAY)
  AND date_column
   >= DATE(DATE_ADD(now(), INTERVAL -1 DAY))

Condition mới hoàn toàn redundant nhưng là một filter trực tiếp trên DATE_COLUMN và có thể được dùng làm access predicate. Dù kỹ thuật này không hoàn hảo, nó thường là một approximation đủ tốt.

Mẹo

Dùng một redundant condition trên column có significance cao nhất khi một range condition kết hợp nhiều column.

Với PostgreSQL, nên dùng row values syntax được mô tả ở trang 151.

Bạn cũng có thể dùng kỹ thuật này khi lưu date và time trong text column, nhưng phải dùng date format và time format tạo ra thứ tự chronological khi sort theo lexical order — ví dụ format được ISO 8601 gợi ý (YYYY-MM-DD HH:MM:SS). Ví dụ sau dùng function TO_CHAR của Oracle database cho mục đích đó:

SQL
SELECT ...
  FROM ...
 WHERE date_string || time_string
     > TO_CHAR(sysdate - 1, 'YYYY-MM-DD HH24:MI:SS')
   AND date_string
    >= TO_CHAR(sysdate - 1, 'YYYY-MM-DD')

Chúng ta sẽ lại gặp vấn đề áp dụng range condition trên nhiều column trong phần “Paging Through Results”. Chúng ta cũng sẽ dùng cùng phương pháp approximation để giảm nhẹ vấn đề.

Đôi khi chúng ta gặp trường hợp ngược lại và muốn cố ý obfuscate condition để nó không còn được dùng làm access predicate. Chúng ta đã xem vấn đề này khi bàn về ảnh hưởng của bind parameter lên LIKE condition. Hãy xét ví dụ sau:

SQL
SELECT last_name, first_name, employee_id
  FROM employees
 WHERE subsidiary_id = ?
   AND last_name LIKE ?

Giả sử có một index trên SUBSIDIARY_ID và một index khác trên LAST_NAME, index nào tốt hơn cho query này?

Không biết vị trí wildcard trong search term thì không thể đưa ra câu trả lời có cơ sở. Optimizer không còn lựa chọn nào khác ngoài việc “đoán”. Nếu biết luôn có leading wildcard, bạn có thể cố ý obfuscate LIKE condition để optimizer không còn xem xét index trên LAST_NAME.

SQL
SELECT last_name, first_name, employee_id
  FROM employees
 WHERE subsidiary_id = ?
   AND last_name || '' LIKE ?

Chỉ cần append một empty string vào column LAST_NAME. Tuy nhiên, đây là option cuối cùng. Chỉ dùng khi thật sự cần thiết.

Smart Logic#

Một trong những tính năng cốt lõi của SQL database là hỗ trợ ad-hoc query: query mới có thể được execute bất cứ lúc nào. Điều này chỉ khả thi vì query optimizer (query planner) hoạt động ở runtime; nó phân tích từng statement khi nhận được và lập tức tạo execution plan hợp lý. Bind parameter có thể giảm overhead do runtime optimization gây ra.

Tóm lại, database được tối ưu cho dynamic SQL — vì vậy hãy dùng nó nếu cần.

Tuy nhiên, có một practice phổ biến là tránh dynamic SQL để dùng static SQL — thường vì myth “dynamic SQL chậm”. Practice này gây hại nhiều hơn lợi nếu database dùng shared execution plan cache như DB2, Oracle database hoặc SQL Server.

Để minh họa, hãy hình dung một application query table EMPLOYEES. Application cho phép search subsidiary id, employee id và last name (case-insensitive) theo mọi tổ hợp. Vẫn có thể viết một query duy nhất bao phủ mọi trường hợp bằng “smart” logic.

SQL
SELECT first_name, last_name, subsidiary_id, employee_id
  FROM employees
 WHERE ( subsidiary_id    = :sub_id OR :sub_id IS NULL )
   AND ( employee_id      = :emp_id OR :emp_id IS NULL )
   AND ( UPPER(last_name) = :name OR :name IS NULL )

Query dùng named bind variable để dễ đọc hơn. Mọi filter expression có thể có đều được viết tĩnh trong statement. Khi không cần một filter, bạn chỉ cần dùng NULL thay cho search term: logic OR sẽ disable condition đó.

Đây là một SQL statement hoàn toàn hợp lý. Việc dùng NULL thậm chí còn phù hợp với định nghĩa của nó theo three-valued logic của SQL. Tuy nhiên, đây lại là một trong những performance anti-pattern tệ nhất.

Database không thể optimize execution plan cho một filter cụ thể vì bất kỳ filter nào cũng có thể bị hủy ở runtime. Database phải chuẩn bị cho trường hợp xấu nhất — khi tất cả filter đều bị disable:

Execution plan
----------------------------------------------------
| Id | Operation         | Name      | Rows | Cost |
----------------------------------------------------
| 0 | SELECT STATEMENT |             |    2 | 478 |
|* 1 | TABLE ACCESS FULL| EMPLOYEES |     2 | 478 |
----------------------------------------------------
Predicate Information (identified by operation id):
---------------------------------------------------
1 - filter((:NAME IS NULL OR UPPER("LAST_NAME")=:NAME)
       AND (:EMP_ID IS NULL OR "EMPLOYEE_ID"=:EMP_ID)
       AND (:SUB_ID IS NULL OR "SUBSIDIARY_ID"=:SUB_ID))

Vì vậy, database dùng full table scan ngay cả khi có index cho từng column.

Không phải database không thể resolve “smart” logic. Database tạo generic execution plan vì bind parameter cho phép plan được cache và re-use với các value khác về sau. Nếu không dùng bind parameter mà viết actual value vào SQL statement, optimizer sẽ chọn index phù hợp cho filter đang active:

SQL
SELECT first_name, last_name, subsidiary_id, employee_id
  FROM employees
 WHERE( subsidiary_id    = NULL     OR NULL IS NULL )
   AND( employee_id      = NULL     OR NULL IS NULL )
   AND( UPPER(last_name) = 'WINAND' OR 'WINAND' IS NULL )

|Id | Operation                   | Name        | Rows | Cost |

---------------------------------------------------------------

---------------------------------------------------

Tuy nhiên, đây không phải là giải pháp. Nó chỉ chứng minh rằng database có thể resolve các condition này.

Warning

Dùng literal value khiến application của bạn dễ bị SQL injection attack và có thể gây performance problem do optimization overhead tăng lên.

Giải pháp hiển nhiên cho dynamic query là dynamic SQL. Theo nguyên tắc KISS, hãy chỉ nói cho database biết bạn cần gì ngay lúc này — và không gì khác.

SQL
SELECT first_name, last_name, subsidiary_id, employee_id
  FROM employees
 WHERE UPPER(last_name) = :name

Lưu ý rằng query này dùng một bind parameter.

Tip

Dùng dynamic SQL nếu bạn cần dynamic where clause.

Vẫn dùng bind parameter khi generate dynamic SQL — nếu không, myth “dynamic SQL chậm” sẽ trở thành sự thật.

Vấn đề được mô tả trong phần này rất phổ biến. Mọi database dùng shared execution plan cache đều có một feature để xử lý nó — thường lại đưa vào những problem và bug mới.

MySQL#

MySQL không gặp vấn đề cụ thể này vì nó hoàn toàn không có execution plan cache. Một feature request từ năm 2009 bàn về ảnh hưởng của execution plan caching. Có vẻ optimizer của MySQL đủ đơn giản để execution plan caching không mang lại lợi ích.

Oracle Database#

Oracle database dùng shared execution plan cache (“SQL area”) và hoàn toàn chịu ảnh hưởng của vấn đề được mô tả trong phần này.

Oracle giới thiệu bind peeking từ release 9i. Bind peeking cho phép optimizer dùng bind value thực tế của lần execute đầu tiên khi chuẩn bị execution plan. Vấn đề của cách tiếp cận này là behavior không deterministic: value của lần execute đầu tiên ảnh hưởng đến mọi lần execute. Execution plan có thể thay đổi khi database restart hoặc, khó đoán hơn, khi cached plan hết hạn và optimizer tạo lại nó bằng các value khác vào lần statement được execute tiếp theo.

Release 11g giới thiệu adaptive cursor sharing để cải thiện tình hình hơn nữa. Feature này cho phép database cache nhiều execution plan cho cùng một SQL statement. Ngoài ra, optimizer peek bind parameter và lưu estimated selectivity của chúng cùng với execution plan.

Khi cache được access sau đó, selectivity của bind value hiện tại phải nằm trong các selectivity range của một cached execution plan thì plan đó mới được re-use. Nếu không, optimizer tạo execution plan mới và so sánh nó với các execution plan đã cache cho query này. Nếu đã có execution plan như vậy, database thay thế nó bằng execution plan mới cũng bao phủ các selectivity estimate của bind value hiện tại. Nếu chưa có, database cache một execution plan variant mới cho query này — dĩ nhiên kèm theo các selectivity estimate.

PostgreSQL#

PostgreSQL query plan cache chỉ hoạt động với statement đang mở — tức là chừng nào bạn còn giữ PreparedStatement mở. Vấn đề được mô tả ở trên chỉ xảy ra khi re-use statement handle. Lưu ý rằng JDBC driver của PostgresSQL chỉ enable cache sau lần execute thứ năm.

SQL Server#

SQL Server dùng parameter sniffing. Parameter sniffing cho phép optimizer dùng bind value thực tế của lần execute đầu tiên trong quá trình parsing. Vấn đề của cách tiếp cận này là behavior không deterministic: value của lần execute đầu tiên ảnh hưởng đến mọi lần execute. Execution plan có thể thay đổi khi database restart hoặc, khó đoán hơn, khi cached plan hết hạn và optimizer tạo lại nó bằng các value khác vào lần statement được execute tiếp theo.

SQL Server 2005 bổ sung các query hint mới để kiểm soát parameter sniffing và việc recompile tốt hơn. Query hint RECOMPILE bypass plan cache cho một statement được chọn. OPTIMIZE FOR cho phép chỉ định các parameter value được dùng riêng cho optimization. Cuối cùng, bạn có thể cung cấp toàn bộ execution plan bằng hint USE PLAN.

Implementation ban đầu của hint OPTION(RECOMPILE) có một bug nên không xem xét tất cả bind variable. Implementation mới được giới thiệu trong SQL Server 2008 lại có một bug khác, khiến tình hình trở nên rất confusing. Erland Sommarskog đã tập hợp toàn bộ thông tin liên quan cho tất cả release của SQL Server.

Math#

Còn một nhóm obfuscation nữa cũng rất “smart” và ngăn index được sử dụng đúng. Thay vì dùng logic expression, nó dùng phép tính.

Hãy xét statement sau. Nó có thể dùng index trên NUMERIC_NUMBER không?

SQL
SELECT numeric_number
  FROM table_name
 WHERE numeric_number - 1000 > ?

Tương tự, statement sau có thể dùng index trên A và B — bạn tự chọn thứ tự — không?

SQL
SELECT a, b
  FROM table_name
 WHERE 3*a + 5 = b

Hãy đặt các câu hỏi này dưới một góc nhìn khác; nếu bạn đang phát triển một SQL database, bạn có bổ sung equation solver không? Phần lớn database vendor chỉ trả lời “No!” và vì vậy, cả hai ví dụ đều không dùng được index.

Bạn thậm chí có thể cố ý dùng phép toán để obfuscate một condition — như chúng ta đã làm trước đó với full text LIKE search. Chỉ cần thêm zero là đủ, chẳng hạn:

SQL
SELECT numeric_number
  FROM table_name
 WHERE numeric_number + 0 = ?

Tuy vậy, chúng ta có thể index các expression này bằng function-based index nếu dùng phép tính theo cách thông minh và biến where clause thành một phương trình:

SQL
SELECT a, b
  FROM table_name
 WHERE 3*a - b = -5

Chúng ta chỉ chuyển các table reference sang một vế và constant sang vế còn lại. Sau đó có thể tạo function-based index cho vế trái của phương trình:

SQL
CREATE INDEX math ON table_name (3*a - b)
