Phụ lục A

Execution Plans

Trước khi database có thể thực thi một SQL statement, optimizer phải tạo execution plan cho statement đó. Sau đó, database thực thi plan này theo từng bước. Ở khía cạnh này, optimizer rất giống một compiler: nó dịch source code (SQL statement) thành một chương trình có thể chạy được (execution plan).

Khi tìm nguyên nhân khiến một statement chạy chậm, execution plan là nơi đầu tiên cần xem. Các section sau giải thích cách lấy và đọc execution plan để tối ưu performance trên nhiều database khác nhau.

Oracle Database#

Hầu hết development environment (IDE) đều hiển thị execution plan rất dễ dàng, nhưng mỗi công cụ lại format plan trên màn hình theo những cách rất khác nhau. Cách được mô tả trong section này cho ra execution plan đúng như dạng xuất hiện xuyên suốt cuốn sách, và chỉ yêu cầu Oracle database release 9iR2 hoặc mới hơn.

Lấy Execution Plan#

Xem execution plan trong Oracle database gồm hai bước:

  1. explain plan for — lưu execution plan vào PLAN_TABLE.
  2. Format và hiển thị execution plan.

Tạo và lưu Execution Plan#

Để tạo execution plan, bạn chỉ cần thêm explain plan for vào trước SQL statement tương ứng:

SQL
EXPLAIN PLAN FOR select * from dual;

Bạn có thể chạy lệnh explain plan for trong bất kỳ development environment nào hoặc trong SQL*Plus. Tuy nhiên, lệnh này không hiển thị plan mà lưu plan vào một table tên là PLAN_TABLE. Từ release 10g, table này tự động có sẵn dưới dạng global temporary table. Với các release trước đó, bạn phải tự tạo table này trong từng schema khi cần. Hãy nhờ database administrator tạo giúp, hoặc xin họ create table statement có sẵn trong bộ cài Oracle database:

SQL
$ORACLE_HOME/rdbms/admin/utlxplan.sql

Bạn có thể chạy statement này trong bất kỳ schema nào bạn muốn để tạo PLAN_TABLE trong schema đó.

Cảnh báo

Lệnh explain plan for không nhất thiết tạo ra cùng execution plan với plan mà database dùng khi thực sự thực thi statement.

Hiển thị Execution Plan#

Package DBMS_XPLAN được giới thiệu từ release 9iR2 và có thể format, hiển thị execution plan từ PLAN_TABLE. Ví dụ sau cho biết cách hiển thị execution plan gần nhất đã được explain trong database session hiện tại:

SQL
select * from table(dbms_xplan.display);

Một lần nữa, nếu statement đó không hoạt động ngay, bạn nên nhờ DBA hỗ trợ.

Query sẽ hiển thị execution plan như trong cuốn sách:

Execution plan
--------------------------------------------------------------
| Id | Operation         | Name | Rows | Bytes | Cost (%CPU)|.
--------------------------------------------------------------
| 0 | SELECT STATEMENT |        |    1 |     2 |     2   (0)|.
| 1 | TABLE ACCESS FULL| DUAL |      1 |     2 |     2   (0)|.
--------------------------------------------------------------

Một số column trong execution plan này đã được bỏ đi để vừa trang hơn trong sách.

Các Operation#

Truy cập Index và Table#

INDEX UNIQUE SCAN

INDEX UNIQUE SCAN chỉ thực hiện B-tree traversal. Database dùng operation này khi một unique constraint bảo đảm search criteria khớp với không quá một entry. Xem thêm Chapter 1, “Anatomy of an Index”.

INDEX RANGE SCAN

INDEX RANGE SCAN thực hiện B-tree traversal, rồi đi theo leaf node chain để tìm tất cả entry khớp. Xem thêm Chapter 1, “Anatomy of an Index”.

Những predicate được gọi là index filter predicate thường gây ra vấn đề performance cho INDEX RANGE SCAN. Section tiếp theo giải thích cách nhận diện chúng.

INDEX FULL SCAN

Đọc toàn bộ index — tất cả row — theo index order. Tùy vào nhiều system statistics khác nhau, database có thể thực hiện operation này nếu cần lấy tất cả row theo index order — chẳng hạn vì có order by clause tương ứng. Thay vào đó, optimizer cũng có thể dùng INDEX FAST FULL SCAN và thực hiện thêm một sort operation. Xem Chapter 6, “Sorting and Grouping”.

INDEX FAST FULL SCAN

Đọc toàn bộ index — tất cả row — theo cách chúng được lưu trên disk. Operation này thường được thực hiện thay cho full table scan nếu mọi column cần thiết đều có trong index. Tương tự TABLE ACCESS FULL, INDEX FAST FULL SCAN có thể hưởng lợi từ multi-block read operation. Xem Chapter 5, “Clustering Data”.

TABLE ACCESS BY INDEX ROWID

Đọc một row từ table bằng ROWID lấy được từ bước index lookup ngay trước đó. Xem thêm Chapter 1, “Anatomy of an Index”.

TABLE ACCESS FULL

Còn được gọi là full table scan. Đọc toàn bộ table — tất cả row và column — theo cách chúng được lưu trên disk. Dù multi-block read operation cải thiện đáng kể tốc độ full table scan, đây vẫn là một trong những operation tốn kém nhất. Ngoài IO rate cao, full table scan phải kiểm tra mọi table row nên cũng có thể tiêu tốn nhiều CPU time. Xem thêm “Full Table Scan” ở page 13.

Joins#

Nhìn chung, mỗi join operation chỉ xử lý hai table một lúc. Nếu query có nhiều join hơn, các join sẽ được thực hiện lần lượt: trước tiên là hai table, sau đó là intermediate result với table tiếp theo. Vì vậy, trong ngữ cảnh join, từ “table” cũng có thể mang nghĩa “intermediate result”.

NESTED LOOPS JOIN

Join hai table bằng cách lấy kết quả từ một table, rồi với từng row của table thứ nhất thì query table còn lại. Xem thêm “Nested Loops” ở page 92.

HASH JOIN

Hash join nạp các candidate record từ một phía của join vào một hash table, sau đó dùng từng row ở phía còn lại của join để probe hash table này. Xem thêm “Hash Join” ở page 101.

MERGE JOIN

Merge join ghép hai sorted list lại với nhau, giống như một chiếc khóa kéo. Cả hai phía của join phải được sort sẵn từ trước. Xem thêm “Sort Merge” ở page 109.

Sorting and Grouping#

SORT ORDER BY

Sắp xếp kết quả theo order by clause. Operation này cần nhiều memory để materialize intermediate result (không pipelined). Xem thêm “Indexing Order By” ở page 130.

SORT ORDER BY STOPKEY

Sắp xếp một subset của kết quả theo order by clause. Operation này được dùng cho top-N query khi không thể thực thi theo kiểu pipelined. Xem thêm “Querying Top-N Rows” ở page 143.

SORT GROUP BY

Sắp xếp result set theo các group by column, rồi aggregate kết quả đã sắp xếp ở bước thứ hai. Operation này cần nhiều memory để materialize intermediate result set (không pipelined). Xem thêm “Indexing Group By” ở page 139.

SORT GROUP BY NOSORT

Aggregate một tập dữ liệu đã được sort sẵn theo group by clause. Operation này không buffer intermediate result mà được thực thi theo kiểu pipelined. Xem thêm “Indexing Group By” ở page 139.

HASH GROUP BY

Group kết quả bằng một hash table. Operation này cần nhiều memory để materialize intermediate result set (không pipelined). Output không được sắp xếp theo bất kỳ thứ tự có ý nghĩa nào. Xem thêm “Indexing Group By” ở page 139.

Top-N Queries#

Hiệu quả của top-N query phụ thuộc vào execution mode của các operation bên dưới. Top-N query sẽ rất kém hiệu quả khi phải dừng giữa chừng các operation không pipelined như SORT ORDER BY.

COUNT STOPKEY

Dừng các operation bên dưới khi đã fetch đủ số row mong muốn. Xem thêm section có tên “Querying Top-N Rows”.

WINDOW NOSORT STOPKEY

Dùng window function (over clause) để dừng quá trình thực thi khi đã fetch đủ số row mong muốn. Xem thêm “Using Window Functions for Pagination” ở page 156.

Phân biệt Access Predicate và Filter Predicate#

Oracle database áp dụng where clause (predicate) theo ba cách khác nhau:

Access predicate (“access”)#

Access predicate thể hiện start và stop condition của leaf node traversal.

Index filter predicate (“filter” cho index operation)#

Index filter predicate chỉ được áp dụng trong quá trình leaf node traversal. Chúng không góp phần tạo nên start và stop condition, cũng không thu hẹp range được scan.

Table level filter predicate (“filter” cho table operation)#

Predicate trên các column không thuộc index được đánh giá ở table level. Để làm được điều đó, database phải tải row từ table lên trước.

Execution plan được tạo bằng DBMS_XPLAN utility (xem “Getting an Execution Plan” ở page 166) cho biết index được sử dụng như thế nào trong phần “Predicate Information” nằm bên dưới execution plan dạng bảng:

Execution plan
------------------------------------------------------
| Id | Operation         | Name       | Rows | Cost |
------------------------------------------------------
| 0 | SELECT STATEMENT |              |     1 | 1445 |
| 1 | SORT AGGREGATE |                |     1 |      |
|* 2 |   INDEX RANGE SCAN| SCALE_SLOW | 4485 | 1445 |
------------------------------------------------------
Predicate Information (identified by operation id):
   2 - access("SECTION"=:A AND "ID2"=:B)
       filter("ID2"=:B)

Số thứ tự trong predicate information ứng với column “Id” của execution plan. Ở column này, database cũng dùng dấu hoa thị để đánh dấu những operation có predicate information.

Ví dụ này, lấy từ chapter “Performance and Scalability”, cho thấy một INDEX RANGE SCAN có cả access và filter predicate. Oracle database có một điểm đặc biệt: một số filter predicate cũng được hiển thị như access predicate — chẳng hạn ID2=:B trong execution plan ở trên.

Quan trọng

Nếu một điều kiện xuất hiện dưới dạng filter predicate thì đó là filter predicate — bất kể nó có được hiển thị thêm dưới dạng access predicate hay không.

Điều này có nghĩa là INDEX RANGE SCAN sẽ scan toàn bộ range thỏa điều kiện "SECTION"=:A, rồi áp dụng filter "ID2"=:B lên từng row.

Filter predicate ở table level được hiển thị tại operation table access tương ứng, chẳng hạn TABLE ACCESS BY INDEX ROWID hoặc TABLE ACCESS FULL.

PostgreSQL#

Các cách được mô tả trong section này áp dụng cho PostgreSQL 8.0 trở lên.

Getting an Execution Plan#

Để lấy execution plan trong PostgreSQL, ta đặt lệnh explain trước SQL statement. Tuy nhiên, có một hạn chế quan trọng: SQL statement có bind parameter (ví dụ $1, $2, v.v.) không thể explain theo cách này — các statement đó phải được prepare trước:

SQL
PREPARE stmt(int) AS SELECT $1;

Lưu ý PostgreSQL dùng "$n" cho bind parameter. Database abstraction layer của bạn có thể ẩn chi tiết này để bạn dùng dấu chấm hỏi như SQL standard quy định.

Sau đó, có thể explain việc thực thi prepared statement như sau:

SQL
EXPLAIN EXECUTE stmt(1);

Cho đến PostgreSQL 9.1, execution plan đã được tạo ngay ở lời gọi prepare, nên không thể tính đến các giá trị thực tế được truyền vào khi execute. Từ PostgreSQL 9.2, việc tạo execution plan được hoãn đến lúc thực thi, nhờ đó có thể tính đến giá trị thực tế của bind parameter.

Ghi chú

Statement không có bind parameter có thể được explain trực tiếp:

SQL
EXPLAIN SELECT 1;

Trong trường hợp này, optimizer luôn tính đến giá trị thực tế trong lúc query planning. Nếu bạn dùng PostgreSQL 9.1 trở về trước và có dùng bind parameter trong chương trình, bạn cũng nên explain với bind parameter để lấy được cùng execution plan đó.

Output của explain plan như sau:

Execution plan
                QUERY PLAN
------------------------------------------
 Result (cost=0.00..0.01 rows=1 width=0)

Output này có thông tin tương tự các execution plan của Oracle xuất hiện xuyên suốt cuốn sách: tên operation (“Result”), cost tương ứng, estimated row count và expected row width.

Lưu ý PostgreSQL hiển thị hai cost value. Giá trị thứ nhất là startup cost, giá trị thứ hai là total cost để thực thi nếu lấy hết toàn bộ row. Execution plan của Oracle chỉ hiển thị giá trị thứ hai.

PostgreSQL explain command có hai option. Option VERBOSE cung cấp thêm thông tin như fully qualified table name — nhưng VERBOSE thường không mấy hữu ích.

Option explain thứ hai là ANALYZE. Option này được dùng rộng rãi, nhưng tôi khuyên bạn đừng tạo thói quen dùng nó một cách tự động, vì nó thực sự thực thi statement. Với select statement, điều này phần lớn vô hại; nhưng khi dùng cho insert, update hoặc delete, nó sẽ thay đổi dữ liệu của bạn. Để tránh vô tình thay đổi dữ liệu, bạn có thể đặt statement trong một transaction rồi rollback sau đó.

Option ANALYZE thực thi statement và ghi lại thời gian thực tế cùng số row thực tế. Thông tin này rất có giá trị khi tìm nguyên nhân của các cardinality estimate sai (tức row count estimate):

SQL
BEGIN;
EXPLAIN ANALYZE EXECUTE stmt(1);
                   QUERY PLAN
--------------------------------------------------
 Result (cost=0.00..0.01 rows=1 width=0)
         (actual time=0.002..0.002 rows=1 loops=1)
 Total runtime: 0.020 ms
ROLLBACK;

Lưu ý plan ở trên đã được format lại cho vừa trang sách. PostgreSQL in các giá trị “actual” trên cùng dòng với các giá trị ước lượng.

Cảnh báo

explain analyze thực thi statement đang được explain, kể cả khi statement đó là insert, update hoặc delete.

Row count là giá trị duy nhất xuất hiện ở cả hai phần — trong số liệu ước lượng lẫn số liệu thực tế. Nhờ đó, bạn có thể nhanh chóng tìm ra các cardinality estimate sai.

Cuối cùng, prepared statement phải được đóng lại:

SQL
DEALLOCATE stmt;

Operations#

Index and Table Access#

Seq Scan

Operation Seq Scan scan toàn bộ relation (table) theo cách được lưu trên disk (giống TABLE ACCESS FULL).

Index Scan

Index Scan thực hiện B-tree traversal, đi qua các leaf node để tìm mọi entry khớp, rồi lấy table data tương ứng. Operation này giống một INDEX RANGE SCAN theo sau là operation TABLE ACCESS BY INDEX ROWID. Xem thêm Chapter 1, “Anatomy of an Index”.

Những predicate được gọi là index filter predicate thường gây ra vấn đề performance cho Index Scan. Section tiếp theo giải thích cách nhận diện chúng.

Index Only Scan (since PostgreSQL 9.2)

Index Only Scan thực hiện B-tree traversal và đi qua các leaf node để tìm mọi entry khớp. Operation này không cần truy cập table, vì index đã có đủ mọi column mà query cần (ngoại lệ: MVCC visibility information). Xem thêm “Index-Only Scan” ở page 116.

Bitmap Index Scan / Bitmap Heap Scan / Recheck Cond

Bài post của Tom Lane trên PostgreSQL performance mailing list rất rõ ràng và cô đọng.

Một Index Scan thông thường lấy từng tuple-pointer một từ index và truy cập ngay tuple đó trong table. Bitmap scan lấy tất cả tuple-pointer từ index trong một lần, sort chúng bằng một data structure “bitmap” nằm trong memory, rồi truy cập các table tuple theo thứ tự vị trí vật lý của tuple.

—Tom Lane¹

Join Operations#

Nhìn chung, mỗi join operation chỉ xử lý hai table một lúc. Nếu query có nhiều join hơn, các join sẽ được thực hiện lần lượt: trước tiên là hai table, sau đó là intermediate result với table tiếp theo. Vì vậy, trong ngữ cảnh join, từ “table” cũng có thể mang nghĩa “intermediate result”.

Nested Loops

Join hai table bằng cách lấy kết quả từ một table, rồi với từng row của table thứ nhất thì query table còn lại. Xem thêm “Nested Loops” ở page 92.

Hash Join / Hash

Hash join nạp các candidate record từ một phía của join vào một hash table (được đánh dấu là Hash trong plan), sau đó dùng từng record ở phía còn lại của join để probe hash table này. Xem thêm “Hash Join” ở page 101.

Merge Join

(Sort) merge join ghép hai sorted list lại với nhau, giống như một chiếc khóa kéo. Cả hai phía của join phải được sort sẵn từ trước. Xem thêm “Sort Merge” ở page 109.

Sorting and Grouping#

Sort / Sort Key

Sắp xếp tập dữ liệu theo các column được liệt kê trong Sort Key. Operation Sort cần nhiều memory để materialize intermediate result (không pipelined). Xem thêm “Indexing Order By” ở page 130.

GroupAggregate

Aggregate một tập dữ liệu đã được sort sẵn theo group by clause. Operation này không buffer lượng lớn dữ liệu (pipelined). Xem thêm “Indexing Group By” ở page 139.

HashAggregate

Dùng một hash table tạm để group các record. Operation HashAggregate không cần tập dữ liệu đã sort sẵn; thay vào đó, nó dùng nhiều memory để materialize intermediate result (không pipelined). Output không được sắp xếp theo bất kỳ thứ tự có ý nghĩa nào. Xem thêm “Indexing Group By” ở page 139.

Top-N Queries#

Limit

Dừng các operation bên dưới khi đã fetch đủ số row mong muốn. Xem thêm “Querying Top-N Rows” ở page 143.

Hiệu quả của top-N query phụ thuộc vào execution mode của các operation bên dưới. Top-N query sẽ rất kém hiệu quả khi phải dừng giữa chừng các operation không pipelined như Sort.

WindowAgg

Cho biết đang dùng window function. Xem thêm “Using Window Functions for Pagination” ở page 156.

Thận trọng

PostgreSQL không thể thực thi top-N query theo kiểu pipelined khi dùng window function.

Phân biệt Access Predicate và Filter Predicate#

PostgreSQL database áp dụng where clause (predicate) theo ba cách khác nhau:

Access Predicate (“Index Cond”)#

Access predicate thể hiện start và stop condition của leaf node traversal.

Index Filter Predicate (“Index Cond”)#

Index filter predicate chỉ được áp dụng trong quá trình leaf node traversal. Chúng không góp phần tạo nên start và stop condition, cũng không thu hẹp range được scan.

Table level filter predicate (“Filter”)#

Predicate trên các column không thuộc index được đánh giá ở table level. Để làm được điều đó, database phải tải row từ heap table lên trước.

PostgreSQL execution plan không hiển thị riêng index access predicate và index filter predicate — cả hai đều xuất hiện dưới dạng “Index Cond”. Vì vậy, phải đối chiếu execution plan với index definition để phân biệt access predicate và index filter predicate.

Ghi chú

PostgreSQL explain plan không cung cấp đủ thông tin để tìm index filter predicate.

Các predicate được hiển thị dưới dạng “Filter” luôn là table level filter predicate — kể cả khi chúng được hiển thị cho một Index Scan operation.

Hãy xem ví dụ sau, vốn xuất hiện lần đầu trong chapter “Performance and Scalability”:

SQL
CREATE TABLE scale_data (
   section NUMERIC NOT NULL,
   id1     NUMERIC NOT NULL,
   id2     NUMERIC NOT NULL
);
CREATE INDEX scale_data_key ON scale_data(section, id1);

Câu select sau filter theo column ID2, vốn không nằm trong index:

Execution plan
PREPARE stmt(int) AS SELECT count(*)
                       FROM scale_data
                      WHERE section = 1
                         AND id2 = $1;
EXPLAIN EXECUTE stmt(1);

                      QUERY PLAN
-----------------------------------------------------
Aggregate (cost=529346.31..529346.32 rows=1 width=0)
  Output: count(*)
  -> Index Scan using scale_data_key on scale_data
     (cost=0.00..529338.83 rows=2989 width=0)
     Index Cond: (scale_data.section = 1::numeric)
     Filter: (scale_data.id2 = ($1)::numeric)

Predicate trên ID2 xuất hiện dưới dạng "Filter" bên dưới operation Index Scan. Lý do là PostgreSQL thực hiện table access như một phần của operation Index Scan. Nói cách khác, operation TABLE ACCESS BY INDEX ROWID của Oracle database được ẩn bên trong operation Index Scan của PostgreSQL. Vì vậy, một Index Scan có thể filter trên những column không nằm trong index.

Quan trọng

Các Filter predicate của PostgreSQL là table level filter predicate — kể cả khi chúng được hiển thị cho một Index Scan.

Khi thêm index từ chapter “Performance and Scalability”, ta thấy tất cả column đều xuất hiện dưới dạng “Index Cond” — bất kể chúng là access predicate hay filter predicate.

SQL
CREATE INDEX scale_slow
          ON scale_data (section, id1, id2);

Execution plan với index mới không hiển thị filter condition nào:

Execution plan
                      QUERY PLAN
------------------------------------------------------
Aggregate (cost=14215.98..14215.99 rows=1 width=0)
  Output: count(*)
  -> Index Scan using scale_slow on scale_data
     (cost=0.00..14208.51 rows=2989 width=0)
     Index Cond: (section = 1::numeric AND id2 = ($1)::numeric)

Lưu ý rằng điều kiện trên ID2 không thể thu hẹp leaf node traversal, vì trong index, column ID1 đứng trước ID2. Tức là Index Scan sẽ scan toàn bộ range thỏa điều kiện SECTION=1::numeric, rồi áp dụng filter ID2=($1)::numeric lên từng row thỏa điều kiện trên SECTION.

SQL Server#

Method được mô tả trong section này áp dụng cho SQL Server Management Studio 2005 trở lên.

Getting an Execution Plan#

Với SQL Server, có vài cách để lấy execution plan. Hai method quan trọng nhất là:

Graphically#

Biểu diễn dạng graphical của SQL Server execution plan dễ truy cập trong Management Studio nhưng khó chia sẻ, vì thông tin predicate chỉ hiển thị khi di chuột qua operation tương ứng (“hover”).

Tabular#

Execution plan dạng tabular khó đọc nhưng dễ copy vì hiển thị toàn bộ thông tin liên quan cùng lúc.

Graphically#

Graphical explain plan được tạo bằng một trong hai button được highlight bên dưới.

Button bên trái giải thích trực tiếp statement đang được chọn. Button bên phải sẽ ghi lại plan ở lần tiếp theo một SQL statement được thực thi.

Trong cả hai trường hợp, graphical representation của execution plan xuất hiện trong tab “Execution plan” của pane “Results”.

Graphical representation khá dễ đọc sau một chút thực hành. Tuy nhiên, nó chỉ hiển thị thông tin cơ bản nhất: các operation và table hoặc index mà chúng tác động lên.

Management Studio hiển thị thêm thông tin khi di chuột qua một operation (mouseover/hover). Điều này khiến việc chia sẻ execution plan với đầy đủ chi tiết trở nên khó khăn.

Tabular#

Biểu diễn dạng tabular của SQL Server execution plan được lấy bằng cách profiling việc thực thi một statement. Command sau bật chế độ đó:

SQL
SET STATISTICS PROFILE ON

Sau khi bật, mỗi statement được thực thi sẽ tạo thêm một result set. Chẳng hạn, select statement tạo ra hai result set — trước tiên là result của statement, sau đó là execution plan.

Execution plan dạng tabular hầu như không dùng được trong SQL Server Management Studio vì StmtText quá rộng để vừa màn hình.

Ưu điểm của cách biểu diễn này là có thể copy mà không làm mất thông tin quan trọng. Điều này rất tiện nếu bạn muốn đăng SQL Server execution plan lên forum hoặc nền tảng tương tự. Trong trường hợp đó, thường chỉ cần copy column StmtText rồi format lại một chút:

SQL
select COUNT(*) from employees;
  |--Compute Scalar(DEFINE:([Expr1004]=CONVERT_IMPLICIT(...))
       |--Stream Aggregate(DEFINE:([Expr1005]=Count(*)))
            |--Index Scan(OBJECT:([employees].[employees_pk]))

Cuối cùng, bạn có thể tắt profiling lại:

SQL
SET STATISTICS PROFILE OFF

Operations#

Index and Table Access#

SQL Server có terminology đơn giản: operation “Scan” đọc toàn bộ index hoặc table, còn operation “Seek” dùng B-tree hoặc physical address (RID, giống Oracle ROWID) để truy cập một phần cụ thể của index hoặc table.

Index Seek

Index Seek thực hiện B-tree traversal và đi qua các leaf node để tìm mọi matching entry. Xem thêm “Anatomy of an Index” ở page 1.

Index Scan

Đọc toàn bộ index — tất cả row — theo index order. Tùy system statistics, database có thể thực hiện operation này nếu cần mọi row theo index order — chẳng hạn vì có order by clause tương ứng.

Key Lookup (Clustered)

Lấy một row từ clustered index. Operation này tương tự Oracle INDEX UNIQUE SCAN cho một Index-Organized-Table (IOT). Xem thêm “Clustering Data” ở page 111.

RID Lookup (Heap)

Lấy một row từ table — giống Oracle TABLE ACCESS BY INDEX ROWID. Xem thêm “Anatomy of an Index” ở page 1.

Table Scan

Còn được gọi là full table scan. Đọc toàn bộ table — tất cả row và column — theo cách chúng được lưu trên disk. Dù multi-block read operation có thể cải thiện đáng kể tốc độ Table Scan, đây vẫn là một trong những operation tốn kém nhất. Ngoài IO rate cao, Table Scan còn phải kiểm tra mọi table row nên có thể tiêu tốn nhiều CPU time. Xem thêm “Full Table Scan” ở page 13.

Join Operations#

Nhìn chung, join operation chỉ xử lý hai table mỗi lần. Nếu query có nhiều join hơn, chúng được thực hiện tuần tự: trước tiên là hai table, sau đó là intermediate result với table tiếp theo. Trong ngữ cảnh join, từ “table” vì vậy cũng có thể có nghĩa là “intermediate result”.

Nested Loops

Join hai table bằng cách lấy result từ một table rồi query table còn lại cho từng row của table thứ nhất. SQL Server cũng dùng nested loops operation để lấy table data sau một index access. Xem thêm “Nested Loops” ở page 92.

Hash Match

Hash match join nạp các candidate record từ một phía của join vào hash table, sau đó dò hash table cho từng row từ phía còn lại của join. Xem thêm “Hash Join” ở page 101.

Merge Join

Merge join kết hợp hai sorted list như một zipper. Cả hai phía của join phải được presort. Xem thêm “Sort Merge” ở page 109.

Sorting and Grouping#

Sort

Sort result theo order by clause. Operation này cần lượng memory lớn để materialize intermediate result (không pipelined). Xem thêm “Indexing Order By” ở page 130.

Sort (Top N Sort)

Sort một subset của result theo order by clause. Dùng cho top-N query nếu pipelined execution không thể thực hiện. Xem thêm “Querying Top-N Rows” ở page 143.

Stream Aggregate

Aggregate một presorted set theo group by clause. Operation này không buffer intermediate result — nó được execute theo pipelined manner. Xem thêm “Indexing Group By” ở page 139.

Hash Match (Aggregate)

Group result bằng hash table. Operation này cần lượng memory lớn để materialize intermediate result (không pipelined). Output không được order theo cách có ý nghĩa nào. Xem thêm “Indexing Group By” ở page 139.

Top-N Queries#

Top

Dừng các operation bên dưới khi đã fetch đủ số row mong muốn. Xem thêm “Querying Top-N Rows” ở page 143.

Hiệu quả của top-N query phụ thuộc vào execution mode của các operation bên dưới. Nó rất kém hiệu quả khi dừng các non-pipelined operation như Sort.

Distinguishing Access and Filter-Predicates#

Database SQL Server dùng ba method khác nhau để áp dụng where clause (predicate):

Access Predicate (“Seek Predicates”)#

Access predicate thể hiện start và stop condition của leaf node traversal.

Index Filter Predicate (“Predicates” hoặc “where” cho index operation)#

Index filter predicate chỉ được áp dụng trong lúc leaf node traversal. Chúng không đóng góp vào start và stop condition, đồng thời không thu hẹp scanned range.

Table level filter predicate (“where” cho table operation)#

Predicate trên các column không thuộc index được đánh giá ở table level. Để làm vậy, database trước hết phải tải row từ heap table.

Section sau giải thích cách nhận diện filter predicate trong SQL Server execution plan. Nội dung dựa trên sample dùng để minh họa tác động của index filter predicate trong Chapter 3.

SQL
CREATE TABLE scale_data (
   section NUMERIC NOT NULL,
   id1     NUMERIC NOT NULL,
   id2     NUMERIC NOT NULL
);
CREATE INDEX scale_slow ON scale_data(section, id1, id2);

Statement mẫu select theo SECTION và ID2:

SQL
SELECT count(*)
  FROM scale_data
 WHERE section = @sec
   AND id2 = @id2

In Graphical Execution Plans#

Graphical execution plan ẩn thông tin predicate trong một tooltip chỉ xuất hiện khi di chuột qua Index Seek operation.

Seek Predicates của SQL Server tương ứng với access predicate của Oracle — chúng thu hẹp leaf node traversal. Filter predicate chỉ được gắn nhãn là Predicates trong graphical execution plan của SQL Server.

In Tabular Execution Plans#

Tabular execution plan có thông tin predicate trong cùng column với nơi các operation xuất hiện. Vì vậy, rất dễ copy và paste toàn bộ thông tin liên quan trong một lần.

SQL
DECLARE @sec numeric;
DECLARE @id2 numeric;
SET STATISTICS PROFILE ON

SELECT count(*)
  FROM scale_data
 WHERE section = @sec
   AND id2 = @id2

SET STATISTICS PROFILE OFF

Execution plan xuất hiện dưới dạng result set thứ hai trong results pane. Sau đây là column StmtText — đã định dạng lại một chút để dễ đọc:

Execution plan
|--Compute Scalar(DEFINE:([Expr1004]=CONVERT_IMPLICIT(...))
     |--Stream Aggregate(DEFINE:([Expr1008]=Count(*)))
          |--Index Seek(OBJECT:([scale_data].[scale_slow]),
             SEEK: ([scale_data].[section]=[@sec])
                    ORDERED FORWARD
             WHERE:([scale_data].[id2]=[@id2]))

Nhãn SEEK mở đầu cho access predicate, còn nhãn WHERE đánh dấu filter predicate.

MySQL#

Method được mô tả trong section này áp dụng cho mọi version của MySQL.

Getting an Execution Plan#

Đặt explain trước một SQL statement để lấy execution plan.

SQL
EXPLAIN SELECT 1;

Plan được hiển thị dưới dạng tabular (đã bỏ một số column ít quan trọng):

Execution plan
~+-------+------+---------------+------+~+------+------------~
~| table | type | possible_keys | key |~| rows | Extra
~+-------+------+---------------+------+~+------+------------~
~| NULL | NULL | NULL           | NULL |~| NULL | No tables...
~+-------+------+---------------+------+~+------+------------~

Thông tin quan trọng nhất nằm trong column TYPE. Dù tài liệu MySQL gọi đây là “join type”, tôi thích gọi nó là “access type” hơn vì thực tế nó chỉ cách data được truy cập. Ý nghĩa của từng type value được mô tả trong section tiếp theo.

Operations#

Index and Table Access#

Explain plan của MySQL dễ tạo cảm giác an toàn giả vì nói rất nhiều về việc index được sử dụng. Dù đúng về mặt kỹ thuật, điều đó không có nghĩa là index đang được dùng hiệu quả. Thông tin quan trọng nhất nằm trong column TYPE của MySQL explain output — nhưng ngay cả keyword INDEX ở đó cũng không cho biết việc indexing có đúng hay không.

eq_ref

Chỉ thực hiện B-tree traversal. Database dùng operation này khi primary key hoặc unique constraint bảo đảm search criteria match không quá một entry. Xem thêm “Anatomy of an Index” ở page 1.

ref, range

Thực hiện B-tree traversal và đi qua leaf node để tìm mọi matching entry (tương tự INDEX RANGE SCAN). Xem thêm “Anatomy of an Index” ở page 1.

index

Đọc toàn bộ index — tất cả row — theo index order (tương tự INDEX FULL SCAN).

ALL

Đọc toàn bộ table — tất cả row và column — theo cách chúng được lưu trên disk. Ngoài IO rate cao, table scan còn phải kiểm tra mọi row trong table nên có thể tạo tải CPU đáng kể. Xem thêm “Full Table Scan” ở page 13.

Using Index (trong column “Extra”)

Khi column “Extra” hiển thị “Using Index”, nghĩa là table không được access vì index có toàn bộ data cần thiết. Hãy nghĩ đến “using index ONLY”. Xem thêm “Clustering Data” ở page 111.

PRIMARY (trong column “key” hoặc “possible_keys”)

PRIMARY là tên của index được tự động tạo cho primary key.

Sorting and Grouping#

using filesort (trong column “Extra”)

“using filesort” trong column Extra cho biết có explicit sort operation — bất kể sort diễn ra ở đâu (main memory hay disk). “Using filesort” cần lượng memory lớn để materialize intermediate result (không pipelined). Xem thêm “Indexing Order By” ở page 130.

Top-N Queries#

implicit: không có “using filesort” trong column “Extra”

MySQL execution plan không hiển thị top-N query một cách rõ ràng. Nếu dùng limit syntax mà không thấy “using filesort” trong extra column, query được execute theo pipelined manner. Xem thêm “Querying Top-N Rows” ở page 143.

Distinguishing Access and Filter-Predicates#

Database MySQL dùng ba cách khác nhau để đánh giá where clause (predicate):

Access predicate (thông qua column “key_len”)#

Access predicate thể hiện start và stop condition của leaf node traversal.

Index filter predicate (“Using index condition”, từ MySQL 5.6)#

Index filter predicate chỉ được áp dụng trong lúc leaf node traversal. Chúng không đóng góp vào start và stop condition, đồng thời không thu hẹp scanned range.

Table level filter predicate (“Using where” trong column “Extra”)#

Predicate trên các column không thuộc index được đánh giá ở table level. Để làm vậy, database trước hết phải tải row từ table.

MySQL execution plan không cho biết condition nào dùng loại predicate nào — chúng chỉ liệt kê các loại predicate đang được sử dụng.

Trong ví dụ sau, toàn bộ where clause được dùng làm access predicate:

SQL
CREATE TABLE demo (
   id1 NUMERIC
 , id2 NUMERIC
 , id3 NUMERIC
 , val NUMERIC);

INSERT INTO demo VALUES (1,1,1,1);
INSERT INTO demo VALUES (2,2,2,2);

CREATE INDEX demo_idx
          ON demo
             (id1, id2, id3);
EXPLAIN
 SELECT *
   FROM demo
  WHERE id1=1
    AND id2=1;
+------+----------+---------+------+-------+
| type | key      | key_len | rows | Extra |
+------+----------+---------+------+-------+
| ref | demo_idx | 12       |    1 |       |
+------+----------+---------+------+-------+

Trong column “Extra” không hiển thị “Using where” hoặc “Using index condition”. Tuy nhiên, index đã được sử dụng (type=ref, key=demo_idx), vì vậy có thể giả định toàn bộ where clause đủ điều kiện làm access predicate.

Có thể dùng key_len value để kiểm tra điều này. Nó cho biết query sử dụng 12 byte đầu tiên của index definition. Để map giá trị này với tên column, bạn “chỉ” cần biết mỗi column cần bao nhiêu storage space (xem “Data Type Storage Requirements” trong tài liệu MySQL). Khi không có NOT NULL constraint, MySQL cần thêm một byte cho mỗi column. Sau cùng, mỗi NUMERIC column trong ví dụ cần 6 byte. Vì vậy, key length bằng 12 xác nhận hai index column đầu tiên được dùng làm access predicate.

Khi filter bằng column ID3 (thay vì ID2), MySQL 5.6 trở lên dùng index filter predicate (“Using index condition”):

SQL
EXPLAIN
 SELECT *
   FROM demo
  WHERE id1=1
    AND id3=1;

+------+----------+---------+------+-----------------------+
| type | key      | key_len | rows | Extra                 |
+------+----------+---------+------+-----------------------+
| ref | demo_idx | 6        |    1 | Using index condition |
+------+----------+---------+------+-----------------------+

Trong trường hợp này, key length bằng sáu nghĩa là chỉ một column được dùng làm access predicate.

Các version MySQL trước đây dùng table level filter predicate cho query này — được nhận diện bởi “Using where” trong column “Extra”:

Execution plan
+------+----------+---------+------+-------------+
| type | key      | key_len | rows | Extra       |
+------+----------+---------+------+-------------+
| ref | demo_idx | 6        |    1 | Using where |
+------+----------+---------+------+-------------+
