Chương 1

Giải phẫu một Index

“Index làm query nhanh” là lời giải thích cơ bản nhất về index mà tôi từng thấy. Dù nó mô tả rất tốt khía cạnh quan trọng nhất của index, nhưng đáng tiếc là chưa đủ cho cuốn sách này. Chương này mô tả cấu trúc index theo cách bớt hời hợt hơn nhưng không đi quá sâu vào chi tiết. Nó cung cấp vừa đủ insight để hiểu các khía cạnh SQL performance được thảo luận xuyên suốt sách.

Index là một cấu trúc riêng biệt trong database, được tạo bằng create index statement. Nó cần disk space riêng và chứa một bản sao dữ liệu table đã được index. Điều đó có nghĩa index hoàn toàn là sự dư thừa. Việc tạo index không thay đổi dữ liệu table; nó chỉ tạo một data structure mới reference đến table. Suy cho cùng, database index rất giống index ở cuối sách: nó chiếm không gian riêng, có tính dư thừa cao và reference đến thông tin thực được lưu ở một nơi khác.

Clustered Index

SQL Server và MySQL (dùng InnoDB) có cách hiểu rộng hơn về “index”. Chúng gọi các table chỉ gồm cấu trúc index là clustered index. Trong Oracle database, các table này được gọi là Index-Organized Tables (IOT). Chương 5, “Clustering Data”, mô tả chúng chi tiết hơn và giải thích ưu điểm, nhược điểm của chúng.

Tìm kiếm trong database index giống tìm kiếm trong danh bạ điện thoại in sẵn. Khái niệm cốt lõi là mọi entry được sắp xếp theo một thứ tự xác định. Tìm dữ liệu trong data set có thứ tự rất nhanh và dễ vì thứ tự sắp xếp quyết định vị trí của mỗi entry.

Tuy nhiên, database index phức tạp hơn danh bạ in sẵn vì nó liên tục thay đổi. Không thể update danh bạ in sẵn cho từng thay đổi vì đơn giản là không có khoảng trống giữa các entry hiện hữu để thêm entry mới. Danh bạ in sẵn tránh vấn đề này bằng cách chỉ xử lý các update tích lũy ở lần in tiếp theo. SQL database không thể chờ lâu như vậy. Nó phải xử lý ngay các insert statement, delete và update, đồng thời giữ thứ tự index mà không di chuyển lượng lớn dữ liệu.

Database kết hợp hai data structure để đáp ứng thách thức này: doubly linked list và search tree. Hai cấu trúc này giải thích phần lớn đặc tính performance của database.

Các Leaf Node của Index#

Mục đích chính của index là cung cấp một biểu diễn có thứ tự của dữ liệu đã được index. Tuy nhiên, không thể lưu dữ liệu tuần tự vì một insert statement sẽ phải di chuyển các entry phía sau để nhường chỗ cho entry mới. Di chuyển lượng lớn dữ liệu rất tốn thời gian, nên insert statement sẽ rất chậm. Giải pháp là thiết lập một thứ tự logic độc lập với thứ tự vật lý trong memory.

Thứ tự logic được thiết lập bằng doubly linked list. Mỗi node có link tới hai entry lân cận, rất giống một sợi xích. Node mới được insert giữa hai node hiện có bằng cách update link của chúng để reference đến node mới. Vị trí vật lý của node mới không quan trọng vì doubly linked list duy trì thứ tự logic.

Data structure này được gọi là doubly linked list vì mỗi node reference đến node đứng trước và node đứng sau. Nó cho phép database đọc index theo chiều xuôi hoặc ngược khi cần. Nhờ vậy có thể insert entry mới mà không di chuyển lượng lớn dữ liệu — chỉ cần thay đổi một số pointer.

Doubly linked list cũng được dùng cho collection (container) trong nhiều ngôn ngữ lập trình.

Database dùng doubly linked list để kết nối các index leaf node. Mỗi leaf node được lưu trong một database block hoặc page, tức đơn vị lưu trữ nhỏ nhất của database. Mọi index block có cùng kích thước — thường là vài kilobyte. Database tận dụng không gian trong từng block tối đa có thể và lưu nhiều index entry nhất có thể vào mỗi block. Điều đó có nghĩa thứ tự index được duy trì ở hai cấp: các index entry trong từng leaf node và các leaf node với nhau bằng doubly linked list.

Hình 1.1 minh họa các index leaf node và kết nối của chúng với dữ liệu table. Mỗi index entry gồm các column được index (key, column 2) và reference đến row tương ứng trong table (qua ROWID hoặc RID). Khác với index, dữ liệu table được lưu trong cấu trúc heap và hoàn toàn không được sắp xếp. Không có quan hệ nào giữa các row được lưu trong cùng một table block, cũng không có kết nối nào giữa các block.

Search Tree (B-Tree)#

Các index leaf node được lưu theo thứ tự tùy ý — vị trí trên disk không tương ứng với vị trí logic theo thứ tự index. Nó giống một danh bạ điện thoại có các trang bị xáo trộn. Nếu bạn tìm “Smith” nhưng mở danh bạ ở “Robinson” trước, hoàn toàn không đảm bảo Smith nằm sau Robinson. Database cần một cấu trúc thứ hai để nhanh chóng tìm entry giữa các trang bị xáo trộn: balanced search tree, gọi ngắn gọn là B-tree.

Hình 1.2 minh họa một index mẫu có 30 entry. Doubly linked list thiết lập thứ tự logic giữa các leaf node. Root node và branch node hỗ trợ tìm kiếm nhanh giữa các leaf node.

Hình làm nổi bật một branch node và các leaf node mà nó reference đến. Mỗi entry của branch node tương ứng với value lớn nhất trong leaf node tương ứng. Tức là 46 trong leaf node đầu tiên, nên entry branch node đầu tiên cũng là 46. Điều này cũng đúng với các leaf node khác, do đó cuối cùng branch node có các value 46, 53, 57 và 83. Theo sơ đồ này, một branch layer được xây dựng cho đến khi tất cả leaf node được một branch node bao phủ. Layer tiếp theo được xây dựng tương tự nhưng nằm trên level branch node đầu tiên. Quy trình lặp lại cho đến khi mọi key vừa trong một node duy nhất là root node. Cấu trúc này là balanced search tree vì tree depth bằng nhau tại mọi vị trí; khoảng cách giữa root node và leaf node là như nhau ở mọi nơi.

Lưu ý

B-tree là balanced tree, không phải binary tree.

Sau khi được tạo, database tự động duy trì index. Nó áp dụng mọi thao tác insert, delete và update vào index, đồng thời giữ tree cân bằng, do đó tạo maintenance overhead cho write operation. Chương 8, “Modifying Data”, giải thích chi tiết hơn.

Hình 1.3 minh họa một phần index để giải thích việc tìm key “57”. Tree traversal bắt đầu từ root node ở phía bên trái. Mỗi entry được xử lý theo thứ tự tăng dần cho đến khi có value lớn hơn hoặc bằng (>=) search term (57). Trong hình, đó là entry 83. Database đi theo reference đến branch node tương ứng và lặp lại quy trình cho đến khi tree traversal đến leaf node.

Quan trọng

B-tree cho phép database nhanh chóng tìm một leaf node.

Tree traversal là operation rất hiệu quả — hiệu quả đến mức tôi gọi nó là sức mạnh thứ nhất của indexing. Nó hoạt động gần như tức thì, ngay cả trên data set khổng lồ. Điều đó chủ yếu nhờ tree balance, cho phép access mọi element với cùng số bước, và thứ hai là nhờ tree depth tăng theo logarit. Nghĩa là tree depth tăng rất chậm so với số leaf node. Index trong thực tế với hàng triệu record có tree depth là bốn hoặc năm. Tree depth là sáu hầu như không thấy. Khung “Logarithmic Scalability” mô tả chi tiết hơn.

Index Chậm, Phần I#

Dù tree traversal hiệu quả, vẫn có trường hợp index lookup không nhanh như mong đợi. Mâu thuẫn này đã nuôi dưỡng huyền thoại về “degenerated index” trong thời gian dài. Huyền thoại này coi index rebuild là giải pháp thần kỳ. Lý do thực sự khiến các statement đơn giản có thể chậm, ngay cả khi dùng index, có thể được giải thích dựa trên các phần trước.

Thành phần đầu tiên của index lookup chậm là leaf node chain. Hãy xét lại việc tìm “57” ở Hình 1.3. Rõ ràng index có hai entry match. Chính xác hơn, có ít nhất hai entry giống nhau: leaf node tiếp theo có thể còn entry khác cho “57”. Database phải đọc leaf node tiếp theo để xem còn entry match nào không. Nghĩa là index lookup không chỉ cần tree traversal mà còn phải đi theo leaf node chain.

Thành phần thứ hai là access table. Ngay cả một leaf node cũng có thể chứa nhiều hit — thường là hàng trăm. Dữ liệu table tương ứng thường phân tán trên nhiều table block (xem Hình 1.1, “Index Leaf Nodes and Corresponding Table Data”). Điều đó có nghĩa mỗi hit cần thêm một lần table access.

Index lookup cần ba bước: (1) tree traversal; (2) đi theo leaf node chain; (3) fetch dữ liệu table. Tree traversal là bước duy nhất có giới hạn trên về số block được access — index depth. Hai bước còn lại có thể cần access nhiều block — chúng gây ra index lookup chậm.

Khả năng Mở rộng Logarit

Trong toán học, logarit của một số theo một cơ số cho trước là lũy thừa hoặc số mũ mà cơ số phải được nâng lên để tạo ra số đó [Wikipedia1].

Trong search tree, cơ số tương ứng với số entry trên mỗi branch node và số mũ tương ứng với tree depth. Index ví dụ ở Hình 1.2 chứa tối đa bốn entry mỗi node và có tree depth là ba. Điều đó nghĩa là index có thể chứa tối đa 64 (43) entry. Nếu tăng thêm một level, nó đã có thể chứa 256 entry (44). Mỗi khi thêm một level, số index entry tối đa tăng gấp bốn. Logarit đảo ngược function này. Vì vậy tree depth là log4(number-of-index-entries).

Sự tăng trưởng logarit cho phép index ví dụ tìm kiếm một triệu record với mười tree level, nhưng index thực tế còn hiệu quả hơn. Yếu tố chính ảnh hưởng tree depth, và do đó ảnh hưởng lookup performance, là số entry trong mỗi tree node. Về mặt toán học, số này tương ứng với cơ số của logarit. Cơ số càng lớn, tree càng nông, traversal càng nhanh.

Database khai thác khái niệm này tối đa và đưa nhiều entry nhất có thể vào mỗi node — thường là hàng trăm. Điều đó có nghĩa mỗi index level mới hỗ trợ số entry nhiều gấp một trăm lần.

Nguồn gốc của huyền thoại “index chậm” là quan niệm sai rằng index lookup chỉ traverse tree, từ đó có ý tưởng rằng index chậm hẳn do tree bị “hỏng” hoặc “mất cân bằng”. Sự thật là bạn có thể hỏi hầu hết database cách chúng dùng một index. Oracle database mô tả khá chi tiết về điều này và có ba operation riêng biệt mô tả một index lookup cơ bản:

INDEX UNIQUE SCAN
INDEX UNIQUE SCAN chỉ thực hiện tree traversal. Oracle database dùng operation này khi unique constraint bảo đảm search criteria match không quá một entry.
INDEX RANGE SCAN
INDEX RANGE SCAN thực hiện tree traversal và đi theo leaf node chain để tìm mọi entry match. Đây là operation dự phòng khi nhiều entry có thể match search criteria.
TABLE ACCESS BY INDEX ROWID
Operation TABLE ACCESS BY INDEX ROWID lấy row từ table. Operation này thường được thực hiện cho mọi record match từ operation index scan đứng trước.

Điểm quan trọng là INDEX RANGE SCAN có thể đọc một phần lớn index. Nếu mỗi row cần thêm một table access, query có thể chậm dù đang dùng index.
