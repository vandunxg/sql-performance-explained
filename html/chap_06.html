Sorting and Grouping

Sorting là một operation tiêu tốn rất nhiều resource. Nó cần khá nhiều CPU time, nhưng vấn đề chính là database phải tạm thời buffer result. Sau cùng, sort operation phải đọc toàn bộ input trước khi có thể tạo output đầu tiên. Sort operation không thể execute theo pipelined manner — điều này có thể trở thành vấn đề với data set lớn.

Index cung cấp một ordered representation của indexed data: principle này đã được mô tả trong Chapter 1. Ta cũng có thể nói index lưu data theo dạng presorted. Thực tế index được sort giống như khi dùng index definition trong order by clause. Vì vậy, không có gì bất ngờ khi ta có thể dùng index để tránh sort operation nhằm đáp ứng order by clause.

Trớ trêu là INDEX RANGE SCAN cũng trở nên inefficient với data set lớn — đặc biệt khi theo sau là table access. Điều này có thể triệt tiêu phần tiết kiệm do tránh sort operation. Trong trường hợp này, FULL TABLE SCAN với explicit sort operation thậm chí có thể nhanh hơn. Một lần nữa, công việc của optimizer là đánh giá các execution plan khác nhau và chọn plan tốt nhất.

Indexed order by execution không chỉ tiết kiệm sorting effort; nó còn có thể trả về các result đầu tiên mà không cần xử lý toàn bộ input data. Vì vậy order by được execute theo pipelined manner. Chapter 7, “Partial Results”, giải thích cách khai thác pipelined execution để implement pagination query hiệu quả. Điều này khiến pipelined order by quan trọng đến mức tôi gọi nó là power thứ ba của indexing.

Chapter này giải thích cách dùng index cho pipelined order by execution. Để làm vậy, chúng ta phải đặc biệt chú ý đến tương tác với where clause cũng như modifier ASC và DESC. Chapter kết thúc bằng việc áp dụng các kỹ thuật này cho group by clause.

Indexing Order By#

SQL query có order by clause không cần explicit sort result nếu relevant index đã trả về row theo đúng order cần thiết. Nghĩa là cùng index được dùng cho where clause cũng phải cover order by clause.

SQL
SELECT sale_date, product_id, quantity
  FROM sales
 WHERE sale_date = TRUNC(sysdate) - INTERVAL '1' DAY
 ORDER BY sale_date, product_id;

Đã có index trên SALE_DATE có thể dùng cho where clause. Tuy nhiên, database phải thực hiện explicit sort operation để đáp ứng order by clause:

Execution plan
---------------------------------------------------------------
|Id | Operation                    | Name       | Rows | Cost |
---------------------------------------------------------------
| 0 | SELECT STATEMENT             |            | 320 |    18 |
| 1 | SORT ORDER BY                |            | 320 |    18 |
| 2 |   TABLE ACCESS BY INDEX ROWID| SALES      | 320 |    17 |
|*3 |    INDEX RANGE SCAN          | SALES_DATE | 320 |     3 |
---------------------------------------------------------------

INDEX RANGE SCAN vốn đã trả result theo index order. Để tận dụng điều này, chúng ta chỉ cần extend index definition để nó tương ứng với order by clause:

SQL
  DROP INDEX sales_date;
CREATE INDEX sales_dt_pr ON sales (sale_date, product_id);
Execution plan
---------------------------------------------------------------
|Id | Operation                   | Name        | Rows | Cost |
---------------------------------------------------------------
| 0 | SELECT STATEMENT            |             | 320 | 300 |
| 1 | TABLE ACCESS BY INDEX ROWID| SALES        | 320 | 300 |
|*2 |   INDEX RANGE SCAN          | SALES_DT_PR | 320 |     4 |
---------------------------------------------------------------

Sort operation SORT ORDER BY biến mất khỏi execution plan dù query vẫn có order by clause. Database khai thác index order và bỏ qua explicit sort operation.

Important

Nếu index order tương ứng với order by clause, database có thể bỏ qua explicit sort operation.

Dù execution plan mới có ít operation hơn, cost value lại tăng đáng kể vì clustering factor của index mới tệ hơn (xem “Automatically Optimized Clustering Factor” ở page 133). Ở thời điểm này chỉ cần ghi nhận rằng cost value không phải lúc nào cũng là indicator tốt cho execution effort.

Với optimization này, chỉ cần scanned index range được sort theo order by clause. Vì vậy, optimization cũng hoạt động trong ví dụ cụ thể này khi chỉ sort theo PRODUCT_ID:

SQL
SELECT sale_date, product_id, quantity
  FROM sales
 WHERE sale_date = TRUNC(sysdate) - INTERVAL '1' DAY
 ORDER BY product_id;

Trong Figure 6.1, ta thấy PRODUCT_ID là sort criterion duy nhất liên quan trong scanned index range. Do đó index order tương ứng với order by clause trong index range này, nên database có thể bỏ qua sort operation.

Optimization này có thể gây behavior bất ngờ khi mở rộng scanned index range:

SQL
SELECT sale_date, product_id, quantity
  FROM sales
 WHERE sale_date >= TRUNC(sysdate) - INTERVAL '1' DAY
 ORDER BY product_id;

Query này không lấy sale của yesterday mà lấy tất cả sale kể từ yesterday. Nghĩa là nó cover nhiều ngày và scan một index range không chỉ được sort theo PRODUCT_ID. Nếu nhìn lại Figure 6.1 và mở rộng scanned index range xuống dưới, ta sẽ thấy lại có các PRODUCT_ID value nhỏ hơn. Vì vậy database phải dùng explicit sort operation để đáp ứng order by clause.

Execution plan
---------------------------------------------------------------
|Id |Operation                    | Name        | Rows | Cost |
---------------------------------------------------------------
| 0 |SELECT STATEMENT             |             | 320 | 301 |
| 1 | SORT ORDER BY               |             | 320 | 301 |
| 2 | TABLE ACCESS BY INDEX ROWID| SALES        | 320 | 300 |
|*3 |   INDEX RANGE SCAN          | SALES_DT_PR | 320 |     4 |
---------------------------------------------------------------

Nếu database dùng sort operation dù bạn kỳ vọng pipelined execution, có thể có 2 lý do: (1) execution plan với explicit sort operation có cost value tốt hơn; (2) index order trong scanned index range không tương ứng với order by clause.

Một cách đơn giản để phân biệt 2 trường hợp là dùng full index definition trong order by clause — tức là điều chỉnh query theo index để loại bỏ nguyên nhân thứ hai. Nếu database vẫn dùng explicit sort operation, optimizer ưu tiên plan này do cost value; nếu không, database không thể dùng index cho order by clause ban đầu.

Tip

Dùng full index definition trong order by clause để tìm lý do của explicit sort operation.

Trong cả 2 trường hợp, bạn có thể tự hỏi liệu có thể đạt pipelined order by execution hay không và đạt bằng cách nào. Để làm vậy, bạn có thể execute query với full index definition trong order by clause rồi inspect result. Bạn thường sẽ nhận ra perception của mình về index là sai, và index order thực tế không đúng như order by clause ban đầu yêu cầu, nên database không thể dùng index để tránh sort operation.

Nếu optimizer ưu tiên explicit sort operation vì cost value, thường là do optimizer chọn execution plan tốt nhất cho full execution của query. Nói cách khác, optimizer chọn execution plan nhanh nhất để lấy record cuối cùng. Nếu database nhận ra application chỉ fetch một vài row đầu, nó có thể chuyển sang ưu tiên indexed order by. Chapter 7, “Partial Results”, giải thích các optimization method tương ứng.

Automatically Optimized Clustering Factor

Database Oracle giữ clustering factor ở mức tối thiểu bằng cách xét ROWID trong index order. Khi 2 index entry có cùng key value, ROWID quyết định order cuối cùng của chúng. Vì vậy index cũng được order theo table order và có clustering factor nhỏ nhất có thể, vì ROWID biểu diễn physical address của table row.

Khi thêm một column khác vào index, bạn insert một sort criterion mới trước ROWID. Database có ít tự do hơn trong việc align index entry theo table order, nên index clustering factor chỉ có thể xấu đi.

Dù vậy, index order vẫn có thể tương ứng gần đúng với table order. Sale của một ngày có lẽ vẫn được cluster cùng nhau trong table cũng như trong index — dù sequence của chúng không còn hoàn toàn giống nhau. Database phải đọc table block nhiều lần khi dùng index SALE_DT_PR — nhưng đó vẫn là các table block giống như trước. Do data thường xuyên được access được cache, performance impact có thể thấp hơn đáng kể so với mức cost value thể hiện.

Indexing ASC, DESC and NULLS FIRST/LAST#

Database có thể đọc index theo cả 2 direction. Điều đó có nghĩa pipelined order by cũng khả thi nếu scanned index range ở đúng order ngược với order được chỉ định trong order by clause. Dù modifier ASC và DESC trong order by clause có thể ngăn pipelined execution, hầu hết database cung cấp cách đơn giản để đổi index order, khiến index có thể dùng cho pipelined order by.

Ví dụ sau dùng index theo reverse order. Nó trả về các sale kể từ yesterday, được order theo date giảm dần và PRODUCT_ID giảm dần.

SQL
SELECT sale_date, product_id, quantity
  FROM sales
 WHERE sale_date >= TRUNC(sysdate) - INTERVAL '1' DAY
 ORDER BY sale_date DESC, product_id DESC;

Execution plan cho thấy database đọc index theo descending direction.

Execution plan
---------------------------------------------------------------
|Id |Operation                    | Name        | Rows | Cost |
---------------------------------------------------------------
| 0 |SELECT STATEMENT             |             | 320 | 300 |
| 1 | TABLE ACCESS BY INDEX ROWID | SALES       | 320 | 300 |
|*2 | INDEX RANGE SCAN DESCENDING| SALES_DT_PR | 320 |      4 |
---------------------------------------------------------------

Trong trường hợp này, database dùng index tree để tìm matching entry cuối cùng. Từ đó, nó đi theo leaf node chain “lên trên” như trong Figure 6.2. Sau cùng, đó là lý do database dùng doubly linked list để xây dựng leaf node chain.

Đương nhiên, điều quan trọng là scanned index range phải ở đúng order ngược với order mà order by clause cần.

Important

Database có thể đọc index theo cả 2 direction.

Ví dụ sau không đáp ứng prerequisite này vì nó trộn modifier ASC và DESC trong order by clause:

SQL
SELECT sale_date, product_id, quantity
  FROM sales
 WHERE sale_date >= TRUNC(sysdate) - INTERVAL '1' DAY
 ORDER BY sale_date ASC, product_id DESC;

Query trước hết phải trả về các sale của yesterday theo thứ tự PRODUCT_ID giảm dần, sau đó là các sale của today, cũng theo PRODUCT_ID giảm dần. Figure 6.3 minh họa process này. Để lấy các sale theo đúng order yêu cầu, database sẽ phải “jump” trong lúc index scan.

Tuy nhiên, index không có link từ sale của yesterday có PRODUCT_ID nhỏ nhất đến sale của today có PRODUCT_ID lớn nhất. Vì vậy database không thể dùng index này để tránh explicit sort operation.

Với những trường hợp như vậy, hầu hết database đều cung cấp một cách đơn giản để điều chỉnh index order theo order by clause. Cụ thể, bạn có thể dùng modifier ASC và DESC trong index declaration:

SQL
    DROP INDEX sales_dt_pr;

CREATE INDEX sales_dt_pr
    ON sales (sale_date ASC, product_id DESC);

Warning

Database MySQL bỏ qua modifier ASC và DESC trong index definition.

Bây giờ index order tương ứng với order by clause nên database có thể bỏ qua sort operation:

Execution plan
---------------------------------------------------------------
|Id | Operation                   | Name        | Rows | Cost |
---------------------------------------------------------------
| 0 | SELECT STATEMENT            |             | 320 | 301 |
| 1 | TABLE ACCESS BY INDEX ROWID| SALES        | 320 | 301 |
|*2 |   INDEX RANGE SCAN          | SALES_DT_PR | 320 |     4 |
---------------------------------------------------------------

Figure 6.4 cho thấy index order mới. Việc thay đổi sort direction của column thứ hai thực chất đảo direction của các mũi tên trong figure trước. Nhờ vậy, mũi tên thứ nhất kết thúc tại nơi mũi tên thứ hai bắt đầu, khiến index có các row theo đúng order mong muốn.

Important

Khi dùng các modifier ASC và DESC kết hợp trong order by clause, bạn cũng phải define index theo cách tương tự để có thể dùng index cho pipelined order by.

Điều này không ảnh hưởng đến khả năng dùng index cho where clause.

ASC/DESC indexing chỉ cần thiết khi sort từng column theo các direction đối nghịch nhau. Nó không cần thiết để đảo order của tất cả column vì database vẫn có thể đọc index theo descending order nếu cần — ngoại lệ duy nhất là secondary index trên index-organized table. Secondary index ngầm thêm clustering key vào index nhưng không cung cấp khả năng chỉ định sort order. Nếu cần sort clustering key theo descending order, bạn không còn lựa chọn nào khác ngoài việc sort tất cả column còn lại theo descending order. Khi đó database có thể đọc index theo reverse direction để lấy order mong muốn.

Ngoài ASC và DESC, SQL standard còn định nghĩa hai modifier ít được biết đến cho order by clause: NULLS FIRST và NULLS LAST. Khả năng kiểm soát rõ ràng việc sort NULL được đưa vào như một optional extension “gần đây” trong SQL:2003. Vì vậy, mức độ hỗ trợ giữa các database khá hạn chế. Điều này đặc biệt đáng lo vì standard không định nghĩa chính xác sort order của NULL. Standard chỉ quy định tất cả NULL phải nằm cạnh nhau sau khi sort, nhưng không nói chúng phải đứng trước hay sau các entry khác. Nói chính xác hơn, bạn cần chỉ định NULL sorting cho mọi column có thể nhận NULL trong order by clause để có behavior được định nghĩa rõ ràng.

Tuy nhiên, thực tế là optional extension này chưa được SQL Server 2012 hoặc MySQL 5.6 implement. Ngược lại, Oracle database đã hỗ trợ NULLS sorting từ trước khi nó được đưa vào standard, nhưng tính đến release 11g, Oracle không chấp nhận nó trong index definition. Vì vậy Oracle database không thể thực hiện pipelined order by khi sort với

NULLS FIRST. Chỉ PostgreSQL database (từ release 8.3) hỗ trợ modifier NULLS trong cả order by clause và index definition.

Overview sau đây tóm tắt các feature được những database khác nhau cung cấp.

Indexing Group By#

SQL database dùng hai group by algorithm hoàn toàn khác nhau. Algorithm thứ nhất là hash algorithm, aggregate các input record trong một temporary hash table. Sau khi xử lý toàn bộ input record, hash table được trả về làm result. Algorithm thứ hai là sort/group algorithm, trước hết sort input data theo grouping key để các row của mỗi group nằm liền kề nhau. Sau đó database chỉ cần aggregate chúng. Nói chung, cả hai algorithm đều cần materialize một intermediate state, nên chúng không được execute theo pipelined manner. Tuy vậy, sort/group algorithm có thể dùng index để tránh sort operation, nhờ đó enable pipelined group by.

Note

MySQL 5.6 không dùng hash algorithm. Tuy nhiên, optimization cho sort/group algorithm vẫn hoạt động như mô tả bên dưới.

Xét query sau. Query này trả về revenue của yesterday được group theo PRODUCT_ID:

SQL
SELECT product_id, sum(eur_value)
  FROM sales
 WHERE sale_date = TRUNC(sysdate) - INTERVAL '1' DAY
 GROUP BY product_id;

Vì đã biết index trên SALE_DATE và PRODUCT_ID từ section trước, sort/group algorithm phù hợp hơn vì INDEX RANGE SCAN tự động trả về các row theo order cần thiết. Nghĩa là database tránh được materialization vì không cần explicit sort operation — group by được execute theo pipelined manner.

Execution plan
---------------------------------------------------------------
|Id |Operation                    | Name        | Rows | Cost |
---------------------------------------------------------------
| 0 |SELECT STATEMENT             |             | 17 | 192 |
| 1 | SORT GROUP BY NOSORT        |             | 17 | 192 |
| 2 | TABLE ACCESS BY INDEX ROWID| SALES        | 321 | 192 |
|*3 |   INDEX RANGE SCAN          | SALES_DT_PR | 321 |     3 |
---------------------------------------------------------------

Execution plan của Oracle database đánh dấu một SORT GROUP BY được execute theo pipelined manner bằng addendum NOSORT. Execution plan của các database khác không nhắc đến sort operation nào.

Pipelined group by có cùng prerequisite với pipelined order by, ngoại trừ việc không có modifier ASC và DESC. Nghĩa là define index với modifier ASC/DESC không nên ảnh hưởng đến pipelined group by execution. Điều tương tự cũng đúng với NULLS FIRST/LAST. Tuy nhiên, có những database không thể sử dụng đúng một ASC/DESC index cho pipelined group by.

Warning

Với PostgreSQL, bạn phải thêm order by clause để index có NULLS LAST sorting có thể được dùng cho pipelined group by.

Oracle database không thể đọc index theo backward direction để execute pipelined group by theo sau bởi order by.

Nếu mở rộng query để xét tất cả sale kể từ yesterday, như trong ví dụ về pipelined order by, điều đó sẽ ngăn pipelined group by vì cùng lý do trước đó: INDEX RANGE SCAN không trả về các row theo order của grouping key (so sánh Figure 6.1 ở page 131).

SQL
SELECT product_id, sum(eur_value)
  FROM sales
 WHERE sale_date >= TRUNC(sysdate) - INTERVAL '1' DAY
 GROUP BY product_id;
Execution plan
---------------------------------------------------------------
|Id |Operation                    | Name        | Rows | Cost |
---------------------------------------------------------------
| 0 |SELECT STATEMENT             |             |   24 | 356 |
| 1 | HASH GROUP BY               |             |   24 | 356 |
| 2 | TABLE ACCESS BY INDEX ROWID| SALES        | 596 | 355 |
|*3 |   INDEX RANGE SCAN          | SALES_DT_PR | 596 |     4 |
---------------------------------------------------------------

Thay vào đó, Oracle database dùng hash algorithm. Ưu điểm của hash algorithm là nó chỉ cần buffer aggregated result, trong khi sort/group algorithm materialize toàn bộ input set. Nói cách khác, hash algorithm cần ít memory hơn.

Cũng như pipelined order by, execution nhanh không phải là khía cạnh quan trọng nhất của pipelined group by execution. Quan trọng hơn là database execute nó theo pipelined manner và trả về result đầu tiên trước khi đọc toàn bộ input. Đây là prerequisite cho các advanced optimization method được giải thích trong chapter tiếp theo.
