Chương 4

Join Operation

Một SQL query bước vào bar và nhìn thấy hai table.

Nó bước đến gần và hỏi: “Tôi join cùng các bạn được không?”

—Nguồn: Không rõ

Join operation biến đổi dữ liệu từ normalized model sang một dạng denormalized, phù hợp với một mục đích xử lý cụ thể. Join đặc biệt nhạy cảm với disk seek latency, vì nó kết hợp các mảnh dữ liệu nằm rải rác. Một lần nữa, đánh index đúng cách là giải pháp tốt nhất để giảm response time. Tuy nhiên, index nào là đúng còn phụ thuộc vào việc query dùng join algorithm nào trong ba join algorithm phổ biến.

Dù vậy, mọi join algorithm đều có một điểm chung: mỗi lần chúng chỉ xử lý hai table. Một SQL query có nhiều table hơn sẽ cần nhiều bước: trước tiên join hai table để tạo một intermediate result set, sau đó join result này với table tiếp theo, và cứ thế tiếp tục.

Join order không ảnh hưởng đến kết quả cuối cùng, nhưng vẫn ảnh hưởng đến performance. Vì vậy, optimizer sẽ đánh giá mọi hoán vị có thể có của join order rồi chọn ra hoán vị tốt nhất. Nói cách khác, chỉ riêng việc optimize một statement phức tạp cũng có thể trở thành vấn đề về performance. Càng nhiều table cần join thì càng có nhiều biến thể execution plan phải đánh giá — nói theo toán học là n! (tăng theo giai thừa), dù điều này không thành vấn đề khi dùng bind parameter.

Quan trọng

Statement càng phức tạp thì dùng bind parameter càng quan trọng.

Không dùng bind parameter chẳng khác gì lần nào cũng compile lại program.

Pipelining Intermediate Result#

Intermediate result giúp giải thích algorithm rất rõ, nhưng điều đó không có nghĩa là database phải materialize nó. Materialize đồng nghĩa với việc phải lưu intermediate result của join đầu tiên trước khi bắt đầu join tiếp theo. Thay vào đó, database dùng pipelining để giảm memory usage. Tức là mỗi row của intermediate result được pipeline ngay sang join operation tiếp theo, nhờ đó không cần lưu lại intermediate result set.

Nested Loops#

Nested loops join là join algorithm cơ bản nhất. Nó hoạt động giống như dùng hai query lồng nhau: outer query (hay driving query) lấy kết quả từ một table, còn query thứ hai chạy cho từng row của driving query để lấy dữ liệu tương ứng từ table còn lại.

Thực ra, bạn hoàn toàn có thể tự dùng “nested select” để implement nested loops algorithm. Tuy nhiên, đó là cách làm rắc rối, vì network latency cộng dồn lên disk latency, khiến tổng response time còn tệ hơn. “Nested select” vẫn rất phổ biến, vì người ta dễ implement chúng mà không hề nhận ra. Object-relational mapping (ORM) tool đặc biệt “helpful” ở điểm này… đến mức cái gọi là N+1 selects problem đã trở nên tai tiếng trong giới làm nghề.

Các ví dụ sau cho thấy những join kiểu “accidental nested select” do các ORM tool khác nhau sinh ra. Các ví dụ này tìm những employee có last name bắt đầu bằng 'WIN' và lấy toàn bộ SALES của các employee đó.

Các ORM này không sinh ra SQL join mà query table SALES bằng các nested select. Hiện tượng này được gọi là “N+1 selects problem”, hay ngắn gọn là “N+1 problem”, vì nếu driving query trả về N row thì tổng cộng sẽ có N+1 select được thực thi.

Java#

Ví dụ JPA dùng interface CriteriaBuilder.

CriteriaBuilder queryBuilder = em.getCriteriaBuilder();
CriteriaQuery<Employees>
     query = queryBuilder.createQuery(Employees.class);
Root<Employees> r = query.from(Employees.class);
query.where(
   queryBuilder.like(
      queryBuilder.upper(r.get(Employees_.lastName)),
      "WIN%"
   )
);

List<Employees> emp = em.createQuery(query).getResultList();
for (Employees e: emp) {
  // process Employee
  for (Sales s: e.getSales()) {
    // process sale for Employee
  }
}

Hibernate JPA 3.6.0 sinh ra N+1 select query:

SQL
select employees0_.subsidiary_id as subsidiary1_0_
       -- MORE COLUMNS
  from employees employees0_
 where upper(employees0_.last_name) like ?
   select sales0_.subsidiary_id as subsidiary4_0_1_
          -- MORE COLUMNS
     from sales sales0_
    where sales0_.subsidiary_id=?
      and sales0_.employee_id=?

   select sales0_.subsidiary_id as subsidiary4_0_1_
          -- MORE COLUMNS
     from sales sales0_
    where sales0_.subsidiary_id=?
      and sales0_.employee_id=?

Perl#

Ví dụ sau minh họa framework DBIx::Class của Perl:

my @employees =
   $schema->resultset('Employees')
          ->search({'UPPER(last_name)' => {-like=>'WIN%'}});

foreach my $employee (@employees) {
   // process Employee
   foreach my $sale ($employee->sales) {
      // process Sale for Employee
   }

SELECT me.employee_id, me.subsidiary_id

PHP#

Ví dụ Doctrine dùng interface query builder:

$qb = $em->createQueryBuilder();
$qb->select('e')

foreach ($r as $row) {
   // process Employee

Bật SQL Logging#

Hãy bật SQL logging trong lúc development và review các SQL statement được sinh ra.

DBIx::Class#

Terminal
export DBIC_TRACE=1 in your shell.

Doctrine#

Chỉ cấu hình SQL logging ở source code — đừng quên tắt nó khi chạy production. Hãy cân nhắc tự xây dựng một logger có thể cấu hình được.

$logger = new \Doctrine\DBAL\Logging\EchoSqlLogger;
$config->setSQLLogger($logger);

Hibernate (native)#

<property name="show_sql">true</property> in App.config or
hibernate.cfg.xml

JPA#

Trong persistence.xml, nhưng còn tùy JPA provider:

<property name="eclipselink.logging.level" value="FINE"/>
<property name="hibernate.show_sql" value="TRUE"/>
<property name="openjpa.Log" value="SQL=TRACE"/>

Hầu hết ORM cũng cho phép bật SQL logging bằng code. Cách này đi kèm rủi ro vô tình deploy setting đó lên production.

Dù là một anti-pattern, cách tiếp cận “nested selects” vẫn giúp giải thích nested loops join khá rõ. Database thực thi join đúng theo cách các ORM tool ở trên đã làm. Vì vậy, đánh index cho nested loops join cũng giống như đánh index cho các select statement đã trình bày ở trên. Cụ thể là một function-based index trên table EMPLOYEES và một concatenated index cho các join predicate trên table SALES:

SQL
CREATE INDEX emp_up_name ON employees (UPPER(last_name));
CREATE INDEX sales_emp ON sales (subsidiary_id, employee_id);

SQL join vẫn hiệu quả hơn cách tiếp cận nested selects — dù thực hiện cùng các index lookup — vì nó tránh được rất nhiều network communication. SQL join vẫn nhanh hơn ngay cả khi tổng lượng dữ liệu truyền đi lớn hơn, do các attribute của employee bị lặp lại ở mỗi sale. Lý do nằm ở hai chiều của performance: response time và throughput; trong computer network, ta gọi chúng là latency và bandwidth. Bandwidth chỉ ảnh hưởng nhỏ đến response time, còn latency thì ảnh hưởng rất lớn. Vì vậy, với response time, số database round trip quan trọng hơn lượng dữ liệu được truyền.

Mẹo

Hãy thực hiện join trong database.

Hầu hết ORM tool đều có cách nào đó để tạo SQL join. Quan trọng nhất có lẽ là chế độ được gọi là eager fetching. Chế độ này thường được cấu hình ở mức property trong entity mapping — ví dụ cho property employees trong class Sales. Khi đó, mỗi lần truy cập table SALES, ORM tool sẽ luôn join table EMPLOYEES. Chỉ nên cấu hình eager fetching trong entity mapping nếu lúc nào bạn cũng cần thông tin chi tiết của employee đi kèm dữ liệu sales.

Eager fetching phản tác dụng nếu bạn không cần các child record mỗi lần truy cập parent object. Với một application kiểu danh bạ điện thoại, việc tải các record SALES khi hiển thị thông tin chi tiết của employee là không hợp lý. Trong những trường hợp khác, bạn có thể cần dữ liệu sales liên quan — nhưng không phải lúc nào cũng cần. Cấu hình tĩnh không phải là giải pháp.

Để đạt performance tối ưu, bạn cần kiểm soát hoàn toàn các join. Các ví dụ sau cho thấy cách đạt độ linh hoạt cao nhất bằng cách kiểm soát cách join tại runtime.

Nested Loops#

Java#

Interface JPA CriteriaBuilder cung cấp method Root<>.fetch() để kiểm soát join. Method này cho phép bạn chỉ định thời điểm và cách join các object được tham chiếu vào main query. Trong ví dụ này, chúng ta dùng left join để lấy tất cả employee, kể cả những employee không có sale.

Cảnh báo

JPA và Hibernate trả về employee cho mỗi sale.

Nghĩa là một employee có 30 sale sẽ xuất hiện 30 lần. Dù rất khó chịu, đây lại chính là behavior đã được đặc tả (EJB 3.0 persistency, paragraph 4.4.5.3 “Fetch Joins”). Bạn có thể tự loại bỏ phần trùng lặp ở parent relation, hoặc dùng function distinct() như trong ví dụ.

CriteriaBuilder qb = em.getCriteriaBuilder();
CriteriaQuery<Employees> q = qb.createQuery(Employees.class);
Root<Employees> r = q.from(Employees.class);
q.where(queryBuilder.like(
    queryBuilder.upper(r.get(Employees_.lastName)),
    "WIN%")
);
r.fetch("sales", JoinType.LEFT);
// needed to avoid duplication of Employee records
query.distinct(true);
List<Employees> emp = em.createQuery(query).getResultList();

Hibernate 3.6.0 sinh ra SQL statement sau:

SQL
select distinct
       employees0_.subsidiary_id as subsidiary1_0_0_
     , employees0_.employee_id as employee2_0_0_
       -- MORE COLUMNS
     , sales1_.sale_id as sale1_0__
  from employees employees0_
  left outer join sales sales1_
          on employees0_.subsidiary_id=sales1_.subsidiary_id
         and employees0_.employee_id=sales1_.employee_id
 where upper(employees0_.last_name) like ?

Query có left join như mong đợi, nhưng cũng có thêm keyword distinct không cần thiết. Đáng tiếc là JPA không có API call riêng để lọc các parent entry bị trùng mà không đồng thời loại bỏ trùng lặp ở các child record.

Keyword distinct trong SQL query là dấu hiệu đáng lo, vì hầu hết database sẽ thực sự lọc các record trùng lặp. Chỉ một số ít database nhận ra rằng trong trường hợp này, primary key vốn đã bảo đảm tính unique. Native Hibernate API giải quyết vấn đề này ở phía client bằng một result set transformer:

Criteria c = session.createCriteria(Employees.class);
c.add(Restrictions.ilike("lastName", 'Win%'));
c.setFetchMode("sales", FetchMode.JOIN);
c.setResultTransformer(Criteria.DISTINCT_ROOT_ENTITY);

List<Employees> result = c.list();

Cách này sinh ra query sau:

SQL
select this_.subsidiary_id as subsidiary1_0_1_
     , this_.employee_id as employee2_0_1_
       -- MORE this_ columns on employees
     , sales2_.sale_id as sale1_3_
       -- MORE sales2_ columns on sales
  from employees this_
  left outer join sales sales2_
          on this_.subsidiary_id=sales2_.subsidiary_id
         and this_.employee_id=sales2_.employee_id
 where lower(this_.last_name) like ?

Cách này tạo ra SQL gọn gàng, không có clause nào ngoài ý muốn. Lưu ý rằng Hibernate dùng lower() cho các query không phân biệt hoa thường — một chi tiết quan trọng khi làm function-based indexing.

Perl#

Ví dụ sau dùng framework DBIx::Class của Perl:

my @employees =
   $schema->resultset('Employees')
          ->search({ 'UPPER(last_name)' => {-like => 'WIN%'}
                   , {prefetch => ['sales']}
                   });

DBIx::Class 0.08192 sinh ra SQL statement sau:

SQL
SELECT me.employee_id, me.subsidiary_id, me.last_name
       -- MORE COLUMNS
  FROM employees me
  LEFT JOIN sales sales
         ON (sales.employee_id = me.employee_id
        AND sales.subsidiary_id = me.subsidiary_id)
 WHERE ( UPPER(last_name) LIKE ? )
  ORDER BY sales.employee_id, sales.subsidiary_id

Lưu ý order by clause này không do application yêu cầu. Database phải sort result set theo đó, và việc này có thể mất một lúc.

Ví dụ sau dùng framework Doctrine của PHP:

   ->from('Employees', 'e')
   ->leftJoin('e.sales', 's')
   ->where("upper(e.last_name) like :last_name")
   ->setParameter('last_name', 'WIN%');
$r = $qb->getQuery()->getResult();

Mẹo

Hãy hiểu rõ ORM của bạn và nắm quyền kiểm soát join.

Nested loops join cho performance tốt nếu driving query trả về một result set nhỏ. Nếu không, optimizer có thể chọn một join algorithm hoàn toàn khác — chẳng hạn hash join được mô tả ở section tiếp theo. Tuy nhiên, điều này chỉ khả thi khi application dùng join để cho database biết application thực sự cần dữ liệu nào.

Hash Join#

Hash join algorithm nhắm vào điểm yếu của nested loops join: rất nhiều lần B-tree traversal khi thực thi inner query. Thay vào đó, hash join load các candidate record từ một phía của join vào một hash table; hash table này có thể được probe rất nhanh cho từng row từ phía còn lại. Tuning hash join đòi hỏi một cách đánh index hoàn toàn khác so với nested loops join. Ngoài ra, cũng có thể cải thiện performance của hash join bằng cách select ít column hơn — một thách thức với hầu hết ORM tool.

Indexing strategy cho hash join rất khác vì không cần index các join column. Chỉ index cho các independent where predicate mới cải thiện performance của hash join.

Mẹo

Index các independent where predicate để cải thiện performance của hash join.

Xét ví dụ sau. Query này select toàn bộ sale trong sáu tháng gần nhất cùng thông tin chi tiết của employee tương ứng:

SQL
SELECT *
  FROM sales s
  JOIN employees e ON (s.subsidiary_id = e.subsidiary_id
                  AND s.employee_id = e.employee_id )
 WHERE s.sale_date > trunc(sysdate) - INTERVAL '6' MONTH

Filter SALE_DATE là where clause độc lập duy nhất — nghĩa là nó chỉ tham chiếu đến một table và không thuộc join predicate.

Bước thực thi đầu tiên là một full table scan để load toàn bộ employee vào hash table (plan id 2). Hash table dùng join predicate làm key. Ở bước tiếp theo, database thực hiện thêm một full table scan trên table SALES và loại bỏ các sale không thỏa điều kiện trên SALE_DATE (plan id 3). Với những record SALES còn lại, database truy cập hash table để lấy thông tin chi tiết của employee tương ứng.

Mục đích duy nhất của hash table là đóng vai trò một cấu trúc tạm thời trong memory, để tránh phải truy cập table EMPLOYEE nhiều lần. Ngay từ đầu, hash table được load một lần là xong, nên không cần index để lấy từng record một cách hiệu quả. Predicate information xác nhận không có một filter nào được áp dụng trên table EMPLOYEES (plan id 2). Query không có independent predicate nào trên table này.

Quan trọng

Indexing join predicate không cải thiện performance của hash join.

Điều này không có nghĩa là không thể đánh index cho hash join. Các independent predicate vẫn có thể được index. Đó là những điều kiện được áp dụng trong một trong hai table access operation. Trong ví dụ trên, đó là filter trên SALE_DATE.

SQL
CREATE INDEX sales_date ON sales (sale_date);

Execution plan sau dùng index này. Tuy nhiên, plan này vẫn dùng full table scan cho table EMPLOYEES, vì query không có independent where predicate nào trên EMPLOYEES.

Khác với nested loops join, việc đánh index cho hash join có tính đối xứng (symmetric). Nghĩa là join order không ảnh hưởng đến cách đánh index. Nếu đảo ngược join order, index SALES_DATE vẫn có thể được dùng để load hash table.

Lưu ý

Cách đánh index cho hash join không phụ thuộc vào join order.

Một cách tiếp cận khá khác để tối ưu performance của hash join là giảm tối đa kích thước hash table. Cách này hiệu quả vì hash join chỉ đạt mức tối ưu khi toàn bộ hash table nằm vừa trong memory. Vì vậy, optimizer sẽ tự động dùng phía nhỏ hơn của join để làm hash table. Execution plan của Oracle hiển thị lượng memory ước tính cần dùng trong column “Bytes”. Trong execution plan ở trên, table EMPLOYEES cần chín megabyte nên là phía nhỏ hơn.

Cũng có thể giảm kích thước hash table bằng cách thay đổi SQL query, chẳng hạn thêm điều kiện để database load ít candidate record hơn vào hash table. Với ví dụ trên, cách này nghĩa là thêm một filter trên attribute DEPARTMENT để chỉ xét nhân viên sales. Cách này cải thiện performance của hash join ngay cả khi không có index trên attribute DEPARTMENT, vì database không cần lưu vào hash table những employee không thể có sale. Khi làm vậy, bạn phải chắc chắn rằng không có record SALES nào thuộc về employee không làm việc trong department tương ứng. Hãy dùng constraint để bảo vệ các giả định của bạn.

Khi giảm kích thước hash table, yếu tố cần quan tâm không phải là số row mà là memory footprint. Thực ra, cũng có thể giảm kích thước hash table bằng cách select ít column hơn — chỉ những attribute bạn thực sự cần:

SQL
SELECT s.sale_date, s.eur_value
     , e.last_name, e.first_name
  FROM sales s
  JOIN employees e ON (s.subsidiary_id = e.subsidiary_id
                  AND s.employee_id = e.employee_id )
 WHERE s.sale_date > trunc(sysdate) - INTERVAL '6' MONTH

Cách này hiếm khi gây bug, vì nếu bỏ nhầm column thì nhiều khả năng bạn sẽ sớm nhận được error message. Dù vậy, cách này vẫn có thể giảm đáng kể kích thước hash table: trong trường hợp này là từ 9 megabyte xuống còn 234 kilobyte — giảm 97%.

Mẹo

Select ít column hơn để cải thiện hash join performance.

Thoạt nhìn, bỏ vài column khỏi SQL statement có vẻ đơn giản, nhưng đây lại là một thách thức thực sự khi dùng object-relational mapping (ORM) tool. Khả năng hỗ trợ cái gọi là partial object còn rất hạn chế. Các ví dụ sau cho thấy một vài cách có thể làm.

Java#

JPA định nghĩa FetchType.LAZY trong annotation @Basic. Thiết lập này có thể được áp dụng ở mức property:

@Column(name="junk")
@Basic(fetch=FetchType.LAZY)
private String junk;

JPA provider được phép bỏ qua thiết lập này:

LAZY strategy là một hint cho persistence provider runtime rằng dữ liệu nên được fetch lazily khi được truy cập lần đầu. Implementation được phép eagerly fetch cả những dữ liệu đã được chỉ định LAZY strategy hint.

—EJB 3.0 JPA, paragraph 9.1.18

Hibernate 3.6 implement lazy property fetching bằng bytecode instrumentation lúc compile. Instrumentation thêm code vào các compiled class để không fetch các LAZY property cho đến khi chúng được truy cập. Cách tiếp cận này hoàn toàn transparent với application, nhưng lại mở ra một chiều mới của N+1 problem: một select cho mỗi record và mỗi property. Điều này đặc biệt nguy hiểm vì JPA không cung cấp cách kiểm soát tại runtime để eager fetch khi cần.

Native query language HQL của Hibernate giải quyết vấn đề bằng clause FETCH ALL PROPERTIES:

select s from Sales s FETCH ALL PROPERTIES
 inner join fetch s.employee e FETCH ALL PROPERTIES
 where s.saleDate >:dt

Clause FETCH ALL PROPERTIES buộc Hibernate eager fetch entity — ngay cả khi dùng instrumented code và LAZY annotation.

Một lựa chọn khác để chỉ load những column được chọn là dùng data transport object (DTO) thay cho entity. Cách này hoạt động giống nhau trong HQL và JPQL: bạn khởi tạo object ngay trong query:

select new SalesHeadDTO(s.saleDate , s.eurValue
                        ,e.firstName, e.lastName)
  from Sales s
  join s.employee e
 where s.saleDate > :dt

Query chỉ select dữ liệu được yêu cầu và trả về object SalesHeadDTO — một Java object đơn giản (POJO), không phải entity.

Perl#

Framework DBIx::Class không đóng vai trò entity manager, nên inheritance không gây ra vấn đề aliasing.¹ Cookbook của framework này cũng hỗ trợ cách tiếp cận này. Schema definition sau định nghĩa class Sales ở hai mức:

package UseTheIndexLuke::Schema::Result::SalesHead;
use base qw/DBIx::Class::Core/;
__PACKAGE__->table('sales');
__PACKAGE__->add_columns(qw/sale_id employee_id subsidiary_id
                             sale_date eur_value/);
__PACKAGE__->set_primary_key(qw/sale_id/);
__PACKAGE__->belongs_to('employee', 'Employees',
           {'foreign.employee_id' => 'self.employee_id'
           ,'foreign.subsidiary_id' => 'self.subsidiary_id'});

package UseTheIndexLuke::Schema::Result::Sales;
use base qw/UseTheIndexLuke::Schema::Result::SalesHead/;
__PACKAGE__->table('sales');
__PACKAGE__->add_columns(qw/junk/);

Class Sales kế thừa từ class SalesHead và bổ sung attribute còn thiếu. Bạn có thể dùng cả hai class tùy nhu cầu. Lưu ý rằng derived class cũng bắt buộc phải có phần table setup.

Bạn có thể fetch toàn bộ thông tin chi tiết của employee bằng prefetch, hoặc chỉ fetch các column được chọn như dưới đây:

my @sales =
   $schema->resultset('SalesHead')
          ->search($cond
                  ,{      join => 'employee'
                   ,'+columns' => ['employee.first_name'
                                   ,'employee.last_name']
                   }
                  );

Không thể chỉ load các column được chọn từ root table — trong trường hợp này là SalesHead.

PHP#

Version 2 của framework Doctrine hỗ trợ chọn attribute tại runtime. Documentation cho biết các partially loaded object có thể hoạt động bất thường, và yêu cầu dùng keyword partial để xác nhận bạn chấp nhận các rủi ro đó. Ngoài ra, bạn phải select tường minh các primary key column:

$qb = $em->createQueryBuilder();
$qb->select('partial s.{sale_id, sale_date, eur_value},'
          . 'partial e.{employee_id, subsidiary_id, '
                     . 'first_name , last_name}')
   ->from('Sales', 's')
   ->join('s.employee', 'e')
   ->where("s.sale_date > :dt")
   ->setParameter('dt', $dt, Type::DATETIME);

SQL được sinh ra chứa các column được yêu cầu, và một lần nữa có thêm SUBSIDIARY_ID cùng EMPLOYEE_ID từ table SALES.

SQL
SELECT s0_.sale_id        AS sale_id0,
       s0_.sale_date      AS sale_date1,
       s0_.eur_value      AS eur_value2,
       e1_.employee_id AS employee_id3,
       e1_.subsidiary_id AS subsidiary_id4,
       e1_.first_name     AS first_name5,
       e1_.last_name      AS last_name6,
       s0_.subsidiary_id AS subsidiary_id7,
       s0_.employee_id AS employee_id8
  FROM sales s0_
 INNER JOIN employees e1_
         ON s0_.subsidiary_id = e1_.subsidiary_id
        AND s0_.employee_id = e1_.employee_id
 WHERE s0_.sale_date > ?

Các object được trả về tương thích với object đã load đầy đủ, nhưng các column bị thiếu vẫn ở trạng thái chưa được khởi tạo. Truy cập vào các column này cũng không gây ra exception.

Sort Merge#

Sort-merge join ghép hai danh sách đã sort lại với nhau, giống như một chiếc khóa kéo (zipper). Cả hai phía của join đều phải được sort theo join predicate.

Sort-merge join cần cùng loại index như hash join, tức là index cho các independent condition để đọc toàn bộ candidate record trong một lần.

Đánh index cho join predicate là vô ích. Cho đến đây, mọi thứ đều giống hệt hash join. Tuy nhiên, sort-merge join có một đặc điểm riêng: tính đối xứng tuyệt đối. Join order không tạo ra khác biệt nào — kể cả về performance. Tính chất này rất hữu ích cho outer join. Với các algorithm khác, hướng của outer join (left hay right) quyết định join order — nhưng với sort-merge join thì không. Sort-merge join thậm chí có thể thực hiện left và right outer join cùng lúc — cái gọi là full outer join.

Sort-merge join hoạt động rất tốt khi các input đã được sort, nhưng nó hiếm khi được dùng vì sort cả hai phía rất tốn kém. Ngược lại, hash join chỉ cần xử lý trước một phía.

Điểm mạnh của sort-merge join thể hiện rõ khi các input đã được sort sẵn. Có thể đạt được điều này bằng cách tận dụng thứ tự của index để tránh hoàn toàn các sort operation. Chapter 6, “Sorting and Grouping”, giải thích chi tiết concept này.

Dù vậy, hash join algorithm vẫn vượt trội trong nhiều trường hợp.
